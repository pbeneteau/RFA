# 03-concurrency-control: concurrency-control theory mapped to the task board and resource claims

Wave 05, dimension 03. Written 2026-08-25. Premise: RFA agents are to run many tasks at once over a shared identity, workspace, memory store and task board; the design under test is ladder rung 6, extending the 10.3 claim lease with a resource key so the board refuses intersecting claims (ownership over locking). Repo read at commit `50f538d`. All web sources fetched 2026-08-25.

---

## Verdict

**Rung 6 is the right shape and it has forty years of prior art behind it, but as stated it is unsound in two places and underspecified in three.** The shape is right because every line of evidence converges on it: Omega showed a shared board with one commit point refusing intersecting resource claims scales to Google-cluster workloads while pessimistic offers and monolithic locks do not (Omega, EuroSys 2013, pp. 355-361); Nomad ships exactly that design in production with a leader-serialized plan queue a small team built; FoundationDB's Resolver is the same intersection check over key ranges at extreme throughput; and the concurrency-for-agents literature of 2026 (CoAgent, and the ICML position paper) measures that both classical alternatives fail for LLM agents, because a model turn is a minutes-long transaction: on ten contended agent workloads OCC aborted 0.95 times per trial and ran SLOWER than serial (0.93x, 1.83x token cost) while 2PL deadlocked 0.81 times per trial for no speedup (1.04x) (CoAgent, arXiv 2606.15376, p. 2). Claiming resources BEFORE the turn spends inference, and refusing rather than waiting, is the only point in the design space that charges conflicts at the cheap moment. The unsound parts: (1) the ladder never says whether a claim's resource set can grow after grant, and if it can, hold-and-wait returns and with it deadlock, which the refuse-not-wait rule was supposed to make structurally impossible; (2) a flat resource key is only sound if one real resource has exactly one canonical key, and RFA's own layout breaks that today (a knowledge clone shared by two packs would carry two per-pack paths, and the intersection check would pass two writers into the same git tree). The underspecified parts: resource claims guard write-write interference only and the spec must say so (write skew through disjoint write sets is exactly PostgreSQL SSI's canonical anomaly and exactly CoAgent's measured canary anomaly); the fence must reach the mutation path, not just the board (Kleppmann's rule is that the RESOURCE checks the token, and today nothing outside `src/store.ts` ever sees `claim_token`); and the grant registry must live on the task object, because the current fence's secret half is a process-local Map that a hub restart silently empties (`src/store.ts:458`).

## The evidence

### 1. The fence RFA has, and the check it still lacks

Kleppmann's fencing argument is two requirements, not one: the lock service issues a monotonically increasing token, and "the resource itself" checks it, rejecting a lower token after a higher one has been seen ("the storage server remembers that it has already processed a write with a higher token number (34), and so it rejects the request with token 33", https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html, fetched 2026-08-25). Jepsen's etcd 3.4.3 analysis is the measured demonstration that the second half is not optional: etcd's Raft-backed lock API still failed mutual exclusion under process pauses ("multiple clients may hold the same etcd lock concurrently, even in healthy clusters with perfectly synchronized clocks"; ~18% of acknowledged updates lost with five processes and 2 s leases), and the fix Jepsen prescribes is exactly Kleppmann's: guard every write with the lock key's revision (https://jepsen.io/analyses/etcd-3.4.3, fetched 2026-08-25).

RFA's board-side fence is real and shipped: `attempt` is the public orderable half and `claim_token` the secret half, minted per `(room, task, attempt)` at claim (`src/store.ts:2516-2517`), honored on `complete`, `update` and `release` (`src/store.ts:2524-2527`, `2541-2542`, `2586-2589`), spec rationale at `spec/RFA-0.1.md:582-584`. Two gaps, both acknowledged in Appendix F's 10.3 row (`spec/RFA-0.1.md:1246`) but worth restating as blocking for this wave:

- A stale token throws `unauthorized`, not `lease_expired` with `{current_attempt, current_owner, task_state}`, so a client cannot distinguish "wrong credentials" from "your lease ended, decide re-claim vs give up" without a human.
- Nothing outside the board ever checks the fence. The resources a task touches (the pack tree, the /memories store, merge-back in rung 5) are Chubby's "servers that do not support sequencers". Chubby's own answer for those was lock-delay, a grace period after a holder dies (Burrows, OSDI 2006, sect. 2.4: the sequencer is "an opaque byte-string" carrying the lock name, mode and generation number, which the recipient server validates; for servers that cannot, lock-delay up to one minute "protects unmodified servers and clients from everyday problems caused by message delays and restarts"). RFA's release-on-offline plus the (pending) restart grace is its lock-delay. But rung 4 and rung 5 introduce hub-side code that CAN check the fence, and R8 says it must: a merge-back that lands after the claim moved to attempt N+1 is precisely token 33 arriving after token 34.

One more repo fact for R7: the secret half lives in a process-local Map by design (`src/store.ts:450-458`, "Process-local, which is honest: a restart invalidates outstanding tokens"). That honesty is correct for a bearer secret. It becomes wrong the moment the same structure holds resource grants, because a grant's job is to make FUTURE claims fail; a hub restart that forgets grants while tasks stay `working` re-admits every intersecting claim. Grants go on the persisted task object.

### 2. Omega: the direct prior art, and what its numbers say about granularity and turn length

Omega is rung 6 run at Google scale: schedulers hold private copies of shared cell state, claim resource sets optimistically, and one atomic commit point accepts or rejects; "the time from state synchronization to the commit attempt is a transaction" (Schwarzkopf et al., EuroSys 2013, p. 355). Three of its measured results transfer directly:

- **Conflict cost scales with transaction duration.** On the 7-day cluster B trace, once per-job decision time reaches about 10 s the mean conflict fraction exceeds 1.0, "so that scheduling a service job requires at least one retry" on average, and scheduler busyness with conflicts ran about 40% above the no-conflict approximation (p. 360). The system stays viable because a retry costs only scheduler CPU.
- **Granularity is worth 2-3x.** Coarse-grained conflict detection (reject a commit if ANYTHING on the target machine changed, a sequence number per machine) raises conflict rate and busyness "by 2-3x" over fine-grained detection; all-or-nothing gang commits roughly double the conflict fraction; "incremental transactions should be the default" (sect. 5.2, p. 361-362).
- **More claimants raise conflicts but the shape holds**: conflict fraction rises with scheduler count yet the model scaled to 32 parallel batch schedulers (p. 358, fig. 9a).

The mapping to RFA inverts one thing and it matters. Omega's transaction is the scheduling DECISION (seconds), and the work runs after commit. If RFA ran the model turn inside the optimistic window (claim nothing, work, validate at complete), the transaction would be minutes long, which is Omega's above-10s regime with the conflict fraction above 1, except each retry burns a multi-minute turn rather than scheduler CPU. So the Omega evidence does not support optimistic agent execution; it supports what rung 6 actually proposes, which is Omega's commit point moved to BEFORE the work: the claim (cheap, milliseconds) is the transaction, and the turn runs under granted ownership. What survives the mapping unchanged is the granularity result: a pack-level resource key is Omega's per-machine sequence number, and it will pay the 2-3x false-conflict tax the moment two runs of one pack want disjoint files. Hence R2's prefix keys, so a claim can be as fine as the plan allows and as coarse as ignorance requires.

Nomad is the existence proof that a small team ships this: parallel schedulers, "optimistically concurrent", with a leader plan queue that "creates allocations when there is no conflict and otherwise informs the scheduler of a failure" (https://developer.hashicorp.com/nomad/docs/concepts/scheduling/how-scheduling-works, fetched 2026-08-25). Its operational scar is the broker, not the claim check: flapping nodes generated combinatorial evaluation storms ("millions of evaluations" in incidents; the blog's worked example: 100 system jobs, 5,000 nodes each carrying 20 service allocations, 10% of nodes missing a heartbeat, gives (500 x 20) + (500 x 100) = 60,000 evaluations), fixed by dedup and batch cancellation of redundant pending evaluations, cutting Raft load over 80% and scheduler load 99% in the v1.4.3 benchmarks (https://www.hashicorp.com/en/blog/load-shedding-in-the-nomad-eval-broker, fetched 2026-08-25). RFA's volumes are nowhere near this, but the lesson generalizes and rhymes with the CLAUDE.md zero-traffic rule: the central claim point needs an answer for its own overload and its own quiet, and "pending claims are idempotent per board snapshot, so duplicates cancel" is the cheap version to remember when requeue ships.

FoundationDB confirms the representation choice: its Resolver holds a short window of committed write RANGES and refuses any commit whose read ranges intersect them, a stateless prefix/range intersection at one commit point that sustains very high throughput; the Resolver does this "by holding the last 5 seconds of committed writes in memory, and comparing a new transaction's reads against this set of commits" (https://apple.github.io/foundationdb/kv-architecture.html, fetched 2026-08-25; the commit-path walkthrough is at https://apple.github.io/foundationdb/read-write-path.html). Ranges, not opaque strings, are the proven shape (R2). The flat-string alternative also exists at scale, GitHub Actions concurrency groups (one running + pending per case-insensitive string key, queue-or-cancel), and its documented limits are instructive: exact-match keys only, replaceable pending slots, and "ordering is not guaranteed" (https://docs.github.com/actions/writing-workflows/choosing-what-your-workflow-does/control-the-concurrency-of-workflows-and-jobs, fetched 2026-08-25). It mutex-es coarse named things; it cannot say "this claim covers that one".

### 3. Why the claim must precede the turn: the long-transaction literature, old and new

Kung and Robinson's OCC paper contains its own counterargument for agents, stated in 1981: a transaction "that has an arbitrarily long read phase" must be validated against the write sets of everything that committed meanwhile; the system keeps only finitely many old write sets, and "if old write sets are unavailable, validation fails, and the transaction is backed up (probably to the beginning)" (ACM TODS 6(2), 1981, p. 220). Their starvation remedy is equally blunt: detect repeated validation failure and rerun the transaction holding the global critical section, "equivalent to write-locking the entire database" (p. 220). Translated: OCC's own authors say long transactions degrade to pessimistic locking under contention. A model turn is a long transaction by construction; the ICML 2026 position paper names this "temporal asymmetry: LLM inference typically spans seconds to minutes, while simple tool calls complete in milliseconds", and shows concurrency-attributable failures dominate MAS benchmarks (67.1% of Silo-Bench failures; inter-agent misalignment 36.9% on MAST) (arXiv 2608.18092, pp. 2, 5).

CoAgent then measured the whole design space on ten contended workloads (arXiv 2606.15376, pp. 1-2): uncoordinated execution passes 13% of trials; 2PL deadlocks 0.81 times per trial and yields no speedup (1.04x) because locks are held across inference; OCC aborts 0.95 times per trial, runs at 0.93x serial speed, and pays 1.83x tokens because every abort discards minutes of inference; their advisory protocol reaches within 5% of serial correctness at 1.4x speedup. CoAgent also names the deeper problem classical CC cannot dodge in agent settings, the functionality gap: agents act on external state ("a kubectl apply must be executed against the cluster to take effect"), which can be neither buffered for OCC nor rolled back for 2PL's deadlock victim (p. 2). RFA already holds the honest position here, inherited from 10.3: a released cross-org task is never auto-failed "because side effects may exist" (`spec/RFA-0.1.md:590`), and Sagas is the principled completion of that stance: for long-lived work, atomicity is abandoned in favor of per-step compensations, with the explicit guarantee "either T1..Tn or T1..Tj, Cj..C1 will be executed" and the explicit warning that others may see partial results (Garcia-Molina and Salem, 1987, p. 250). The Sagas introduction also cites the quantitative reason locks and long work cannot mix, from Gray's 1981 analysis: "the deadlock frequency grows with the fourth power of the transaction size" (p. 249).

The conclusion is not close: partition at assignment. Charge the conflict at claim time, where a refusal costs one cheap call, never at completion, where it costs a turn.

### 4. Refuse-and-retry is deadlock-free only if the ladder adds one sentence

By the Coffman conditions, deadlock needs mutual exclusion, hold-and-wait, no preemption, and circular wait (Aspnes, Yale CS notes, https://www.cs.yale.edu/homes/aspnes/pinewiki/Deadlock.html, fetched 2026-08-25). A board that grants a claim's whole resource set atomically and REFUSES intersecting claims (nobody ever waits holding something) breaks two conditions at once. PostgreSQL SSI is the production demonstration of the same shape one level up: its SIREAD predicate locks detect intersections and never block, so they cannot deadlock, and the price is false positives whose rate is set by lock granularity (Ports and Grittner, VLDB 2012, sects. 1, 3.3).

The ladder as written omits the load-bearing premise: **the resource set must not grow while held, or growth must itself be refuse-not-wait**. Agents cannot declare complete write sets up front; CoAgent rejects static write partitioning precisely because it "requires the write set to be known in advance, which is often impossible for agents whose plans emerge during execution" (p. 2). So widening requests WILL happen, and the moment a widening waits, hold-and-wait is back: run A holds `pack/x` and waits for `knowledge/k`, run B holds `knowledge/k` and waits for `pack/x`. R5 keeps the freedom and the safety: widening is a fresh mini-claim, refused-not-queued, and refusal never damages the grant already held; the worker's options are to proceed within its grant, release and re-claim wider, or escalate.

The two residual failure modes are the classical ones, and both have named remedies:

- **Starvation of wide claims.** Aspnes states it for atomic acquisition generally: a process "may starve waiting for a group of resources that never become free all at the same time". Kung-Robinson's fallback (after repeated losses, stop being optimistic for this claimant) becomes R5's reservation. The fully fair alternative is ZooKeeper's lock recipe: ephemeral sequential znodes, each waiter watching only its predecessor so "the removal of a node will only cause one client to wake up... you avoid the herd effect", giving FIFO order (https://zookeeper.apache.org/doc/r3.5.7/recipes.html, fetched 2026-08-25). It parks (R11): queueing is real machinery, GitHub Actions' documented "ordering is not guaranteed" shows even huge operators keep it loose, and RFA has no measured refusal rate yet.
- **Stale claims.** Already solved by 10.3's lease: expiry is the owner's presence lease, release on offline/leave/evict, spec 10.3 (`spec/RFA-0.1.md:580, 586`). Gray and Cheriton's model says what the term buys: short terms bound recovery delay and false sharing, long terms cut renewal traffic, most of the benefit arrives by "a term of just a few seconds" (10 s cut consistency traffic to 10% of a zero term), and a recovering server "must honor the leases it granted before it crashed", most easily by waiting out the maximum term (SOSP 1989, pp. 203-205). RFA's coupling of claim expiry to the 180 s presence lease means task recovery after a silent crash is bounded by presence expiry, well inside the same order as Chubby's 12 s KeepAlive + 45 s grace and Kubernetes' lease durations. No independent task TTL is needed while that holds; the number to watch is the pending restart grace ("one full lease period", `spec/RFA-0.1.md:593`), which is Gray-Cheriton's honor-the-maximum-term rule verbatim.

### 5. Granularity: hierarchical keys, the DAG trap, and what claims do NOT guard

Gray, Lorie, Putzolu and Traiger posed the exact question rung 6 must answer: lockable-unit size trades concurrency against overhead, so let granularities coexist in one hierarchy, with intention modes (IS/IX/SIX) tagging ancestors so that a coarse lock and a fine lock detect each other at the ancestor ("locks are requested root to leaf, and released leaf to root", Modelling in Data Base Management Systems, 1976, pp. 365-369). RFA does not need the mode lattice, because claims are all exclusive (writers) and reads are unguarded; collapsing the hierarchy into prefix keys (R2) preserves the one property that matters, cheap ancestor conflict detection: `pack/writer` intersects `pack/writer/notes/a.md` by prefix test alone.

Two Gray 1976 lessons transfer with their teeth intact:

- **The DAG rule.** For non-tree resource graphs the protocol requires locking ALL parents, "to lock a subgraph one must implicitly or explicitly lock all ancestors of the subgraph in the appropriate mode (for a tree there is only one parent)" (p. 370). RFA's resource space is a DAG today: a knowledge clone is tracked under a pack directory, and nothing stops two packs tracking the same remote. Per-pack paths would give one real git tree two unrelated keys, and the intersection check would admit two concurrent writers. R3 is the tree-ification: every shared real resource gets one canonical root key. This is the concurrency twin of the CLAUDE.md knowledge rule (one fact, one file); the failure mode is the same phantom, honest machinery reporting no conflict while the conflict sits under the other name.
- **Coarse claims discriminate.** "Such a coarse unit discriminates against transactions which only want to lock one member of the file" (p. 366). A pack that always claims its whole tree serializes itself; per-run scratch dirs (ladder rung 4) are what make fine claims TRUE, and the two rungs should ship as one story: the scratch dir is the fine-grained resource the claim names.

What the claim board must not pretend to solve: **stale reads through disjoint write sets**. SSI's founding anomaly is write skew, two transactions reading overlapping state and writing disjoint targets, each correct alone, jointly violating the invariant (Ports and Grittner, sect. 2.1.1); CoAgent measured the agent version live on a Kubernetes cluster (agent A repairs images, agent B clones a bad image into a canary; "disjoint write sets address neither of the two relevant ACID properties... partitioning constrains writes; the bug is in the reads", pp. 3-4, fig. 1). Read-set claims are not a fix RFA can buy: agent read sets are "broad and opaque rather than statically inferable" (CoAgent, p. 1), and SSI's own false-positive rate is the cost of approximating them even inside a database. R6 therefore scopes the mechanism honestly in the spec: claims prevent write-write interference; read staleness is owned by 10.4 verification, task idempotency, and (rung 5) merge review. SQS documents the same honesty for its lease: at-least-once redelivery when processing outlives the visibility timeout is designed behavior, mitigated by heartbeat extension and idempotent consumers, never abolished (https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html, fetched 2026-08-25). Parallelism raises the frequency of these cases; it does not create them.

### 6. Fences per resource, crash recovery by reconciliation, and the two-lease clarification

Kafka's KIP-1251 is the cleanest statement that when the RESOURCE becomes the unit of ownership, the fence wants to live there too: zombie owners after partition reassignment are caught by an assignment epoch per (partition, member), validated as `Assignment Epoch <= Client-Side Member Epoch <= Broker-Side Member Epoch`, because the group-level epoch alone either misses zombies or rejects innocents (https://cwiki.apache.org/confluence/spaces/KAFKA/pages/399279344/KIP-1251+Assignment+epochs+for+consumer+groups, fetched 2026-08-25). RFA's fence is per `(task_id, attempt)`; once a resource grant can outlive its task (a queued merge-back, a deferred write), a stale holder of the RESOURCE is invisible to the task-scoped fence. That is R10, parked with a precise trigger, because in v1 grants die with claims and the task fence covers everything.

For crash recovery mid-merge (the ladder's own open question), the strongest prior art is not a locking discipline at all but Kubernetes' controller pattern: optimistic writes (resourceVersion, 409, re-read, retry) paired with level-triggered reconciliation, so a controller that dies mid-change is repaired by the next reconcile observing ACTUAL state and converging, with no unlock cleanup to forget (kubernetes.io controller-runtime cache post, 2026-07-29; the Lease API itself is the same philosophy applied to liveness: `holderIdentity`, `leaseDurationSeconds`, `renewTime`, takeover by claiming the stale object, https://kubernetes.io/docs/concepts/architecture/leases/, fetched 2026-08-25). R9: rung 5's merge-back defines a reconcile ("for every task in `working` with a worktree, compare worktree state against the claim's attempt; merge, requeue, or release"), and the restart path just runs it.

Finally, a wording correction to the ladder before anyone builds from it: "extend the claim lease (10.3) with a resource key" names one lease, but the repo has two lease systems with different jobs. The room-task claim lease (presence-derived, `src/store.ts:2508-2510`) is where resource keys belong; the account lease table (`src/account.ts:173-182`, SQLite, TTL + renew + PID-liveness sweep, capping model turns in flight at `agents.max_inflight`) is a THROUGHPUT governor, not an ownership record, and it already does its job across processes. Temporal's vocabulary keeps the same two things separate for the same reason: worker slot caps govern capacity, task tokens and timeouts govern ownership of a specific piece of work (https://docs.temporal.io/task-queue, fetched 2026-08-25). Rung 6 touches only the first system.

## What this dimension could not verify

The FOR-UPDATE-SKIP-LOCKED article the scout cited as convergent evidence (per-row job claims cannot express cross-row resource constraints; fix is a second resource-keyed advisory lock) returned HTTP 403 on 2026-08-25 and its claim is reported here on the scout's description only; the surrounding evidence (SSI write skew, GitHub Actions concurrency groups, CoAgent) carries the same conclusion independently, so nothing in the verdict rests on it. Temporal's exact worker-liveness bound (the "5 minutes without polling" figure in the scout claim) is not stated on the task-queue page fetched and was not verified. Omega's figures are simulator results (lightweight plus trace-driven high-fidelity), not measurements of a deployed Omega; the paper is explicit about this, and Nomad is cited here as the production confirmation of the architecture rather than of the specific numbers. CoAgent and the position paper are 2026 arXiv preprints; CoAgent's measured trials are its authors' own benchmark and no independent replication was found. The Chubby lock-delay default ("up to some bound, currently one minute") is 2006 Google practice and the right ORDER for RFA's restart grace, not a portable constant. Finally, the claim-token principal-binding rule of 10.3 (same `peer_id` or same authenticated principal) is specified but PENDING in code (Appendix F row 10.3), so the re-bind path this note relies on is bearer-token-only at commit `50f538d`; that is recorded in Appendix F and was not re-tested live here.
