# 04-memory-concurrency: Concurrent writes to agent memory

Wave 05, dimension 04. Written 2026-08-25.
Premise: RFA's memory is an append-only episode log plus a facts store distilled when idle plus a file-backed /memories store the model edits directly; the ladder proposes one in-process lock on /memories (rung 1) and per-conversation concurrency (rung 2). Repo read at commit 50f538d.
All web sources fetched 2026-08-25. Papers cited below were downloaded to `../papers/` and read at page level.

## Verdict

**Serialize-the-writes is the answer every shipped system gives, and none of them merges: Letta documents that concurrent requests to one agent cause race conditions and ships 409 CONFLICT plus retry, Graphiti bounds ingestion with a semaphore and queues episodes, LangMem debounces all memory writing into a single delayed background pass, and ChatGPT publishes no concurrency contract at all. So rung 2 (parallel across conversations, serial within one) is independently validated and rung 1 is directionally right, but the ladder aims the lock at the wrong layer and misses the two failures that arrive first. First, RFA already has a cross-process write race today, before any concurrency rung ships: `rfa agent reflect --apply` (src/reflect.ts:189) and the resident's consolidation timer (src/resident.ts:888) both open FactStore on the same `state/memory.db`, and `FactStore.apply` is a check-then-insert with no transaction and a non-unique hash index (src/memoryfs.ts:358-371), the exact TOCTOU shape confirmed as a silent-duplicate bug in Mem0 (issue #6531). Second, MemClaw's live evaluation showed the pipeline-ordering failure RFA's MemoryGate reproduces by construction: a synchronous near-duplicate gate rejected 206 of 400 contradictory writes before the asynchronous contradiction detector ever saw them, capping contradiction detection at 0.490; RFA's gate silently drops facts at the same door (src/memoryfs.ts:354-357). The deep result of the survey is negative and useful: no production system merges two diverged agent-memory replicas; the shipped patterns are ownership (one writer per block, Letta sleep-time; one manager per memory type, MIRIX), partition (one queue per group_id, Graphiti), and deferral (background consolidation, LangMem/ChatGPT). Merge-on-reconvergence exists only in research (StateFuse's conflict-preserving CRDT contract), so the ladder's replicas-with-diverging-memories postscript is genuinely open territory, and RFA's bi-temporal fact columns are the one asset that would make a future merge order-tolerant. Concurrency also multiplies the poisoning write path (MINJA: 98.2% injection success via queries alone, and the similarity-filter defense class is the weakest), so the gate cannot remain the only line once parallel conversations land.**

## 1. Repo ground truth (commit 50f538d)

- The /memories store is plain filesystem read-modify-write with no lock: `strReplace` reads, checks old_str is present exactly once, replaces, writes back (src/memoryfs.ts:92-102); `insert` splices by line number with no precondition at all (src/memoryfs.ts:104-113); `create` overwrites unconditionally (src/memoryfs.ts:84-90). The unique-old_str check is an accidental optimistic-concurrency guard: if the file changed under the caller such that old_str vanished, the call fails; if the change left old_str intact, the caller silently clobbers it. `insert` has not even the accident.
- Episodes and facts share one SQLite file in WAL mode, opened as two connections in the resident (src/resident.ts:154-155). Facts are written only by consolidation and by reflect; the answer path only reads (src/resident.ts:1052-1056) and records episodes.
- `FactStore.apply` is check-then-insert: `SELECT id FROM facts WHERE hash = ? AND expired_at IS NULL` then a separate `INSERT` (src/memoryfs.ts:358-371), no transaction, and `idx_facts_hash` is not UNIQUE (src/memoryfs.ts:245). Gate-rejected items return `"skipped"` with no trace (src/memoryfs.ts:354-357).
- Consolidation runs on a 60 s timer, deferred while serving, after 8 gated exchanges or 6 h (src/resident.ts:882-899); the pass itself reads a watermark, processes a batch, writes facts, advances the watermark (src/consolidate.ts:104-152). Nothing prevents a second process from running the same pass: `consolidate()` takes any hubdir and opens its own connections (src/consolidate.ts:92-105), and `rfa agent reflect --apply` opens FactStore on the same `state/memory.db` from the CLI process (src/reflect.ts:189, 217) while the resident may be mid-consolidation. Two writers to the facts store exist today.
- SDK sessions are keyed per conversation in an in-memory map (src/resident.ts:156), resumed per turn (src/resident.ts:687) and updated on init (src/resident.ts:699); the process-wide turn lock (src/turnlock.ts) is currently the only thing keeping two turns from resuming one session id. Dimension 05 covers the session side; the memory corollary is below.

## 2. The shipped baseline: serialize and reject, never merge

**Letta (the shipped MemGPT) draws exactly RFA's rung 2 line.** Its docs state "The `agents.messages.create` endpoint is not thread-safe - concurrent requests to the same agent can cause race conditions", and the sanctioned answer is "If you need to send messages to an agent from multiple threads or processes simultaneously, use separate conversations. Each conversation has its own message stream" (https://docs.letta.com/guides/core-concepts/messages/conversations, fetched 2026-08-25). The same page carries the corollary the ladder misses: "The agent's core memory ... is shared across all conversations. When the agent updates a memory block in one conversation, that change is visible in all other conversations." Parallel conversations make the shared memory store the conflict surface immediately; hence recommendation 4.

**Letta also publishes the only per-verb concurrency contract found anywhere**: `memory_insert` (append) is concurrent-safe; `memory_replace` "fails if target string changed", which is built-in optimistic concurrency; `memory_rethink` (whole-block rewrite) is last-writer-wins, the docs name "lost updates" as the outcome of two agents rethinking one block, and the guidance is "Designate one agent (or sleep-time memory) as the 'owner' for heavy edits" (https://docs.letta.com/guides/agents/multi-agent-shared-memory, fetched 2026-08-25). RFA's `strReplace` already carries the memory_replace property by accident; recommendation 2 is that table applied to src/memoryfs.ts.

**The sleep-time architecture is ownership enforced by tool declaration, which is RFA's own posture doctrine.** Letta's design: "the primary agent is not provided with tools to edit its core memory"; the memory tools "are attached to the sleep-time agent, which has the ability to manage both the in-context memory of the primary agent as well as its own", and it edits "in an 'anytime' fashion - so the primary agent can read from this memory whenever" (https://www.letta.com/blog/sleep-time-compute/, fetched 2026-08-25). A two-writer system made safe not with locks but by removing the write tools from one writer. That is recommendation 3, and it costs RFA nothing doctrinally: tools are already the declaration (CLAUDE.md; src/posture.ts).

**When Letta must handle same-agent concurrency anyway, it rejects**: the changelog entry for 0.18.3 reads "Fixed pre-stream `409 CONFLICT` busy handling to resume server-side runs" (https://docs.letta.com/reference/changelog, fetched 2026-08-25). Serialize, reject the overlap, retry: no merge anywhere in the product.

**Graphiti/Zep partition and serialize per partition.** Graphiti's ingestion concurrency is a semaphore: "By default, `SEMAPHORE_LIMIT` is set to `10` concurrent operations to help prevent `429` rate limit errors" (https://github.com/getzep/graphiti README, fetched 2026-08-25), the MCP server ships "Queue-based Processing: Asynchronous episode processing with configurable concurrency limits", and Zep's docs note that batch (concurrent) ingestion forfeits exactly the property that makes memory memory: `add_episode_bulk` skips edge invalidation and is "only for populating empty graphs" (https://help.getzep.com/graphiti/core-concepts/adding-episodes, fetched 2026-08-25). And when the per-partition discipline slipped, the failure was silent cross-contamination: issue #1331 (open, filed 2026-03-19) shows two concurrent `add_episode` calls racing on a shared `self.driver` so "data [is] silently written to wrong FalkorDB graph" (https://github.com/getzep/graphiti/issues/1331, fetched 2026-08-25). Concurrency bugs in memory systems do not crash; they corrupt quietly.

**LangMem's answer is architectural: debounce everything into one background writer.** "If new messages arrive before then: 1. Cancel pending processing task 2. Reschedule with new messages included", with a suggested delay of 30 to 60 minutes, because processing mid-conversation gives "Redundant work ... [and] Incomplete context" (https://langchain-ai.github.io/langmem/guides/delayed_processing/, fetched 2026-08-25). This is RFA's consolidation timer generalized, and it implies the serialization point that matters at scale is the consolidator, not a mutex on the hot path.

**ChatGPT, the largest deployment, documents no contract at all** (negative finding). The Memory FAQ describes automatic background saving and user-facing controls but nothing about ordering, concurrency, or conflicts between simultaneous chats (https://help.openai.com/en/articles/8590148-memory-faq; direct fetch returned HTTP 403 on 2026-08-25, content confirmed via search snapshots and the help-center index). The closest public mechanics are reverse-engineered: memories stored as timestamped sequential entries, several system-prompt sections "probably created/updated by OpenAI out of band on regular cadence", and the author's explicit caveat "The details of the implementation are not known" (https://embracethered.com/blog/posts/2025/chatgpt-how-does-chat-history-memory-preferences-work/, fetched 2026-08-25). The industry norm for memory concurrency is deferral plus silence.

**The original MemGPT paper is single-loop by construction.** The queue manager "appends the incoming messages to the FIFO queue ... and triggers the LLM inference"; "During each inference cycle, LLM processor takes main context (concatenated into a single string) as input"; events "trigger LLM inference" one at a time and the processor yields until the next event (../papers/memgpt-llms-as-operating-systems.pdf, pp. 2-4, sect 2.2-2.4). The entire lineage that RFA's memory copies was designed with exactly one writer, which is why none of the descendants had a concurrency story until production forced one.

## 3. What breaks first in RFA, with the production bug that proves each

**The facts store TOCTOU is Mem0 issue #6531 with the same shape.** The confirmed Mem0 bug: "Two `add()` calls extracting the identical fact for the same scope, awaited concurrently ... both take their snapshot before either inserts, both pass dedup, and both insert - producing a permanent duplicate memory ... No error is raised; the duplication is silent. Although Node runs on a single event loop, the interleaving `await`s between the snapshot and the insert are exactly the race window - a purely-async TOCTOU" (https://github.com/mem0ai/mem0/issues/6531, filed 2026-07-23, open, fetched 2026-08-25). RFA's `apply` is synchronous inside one process (better-sqlite3), so in-process it is safe; across processes (resident timer vs `reflect --apply`, or any future parallel consolidation) the SELECT and INSERT of two writers interleave freely under WAL. Recommendation 1 is a transaction plus a UNIQUE partial index; SQLite makes both one-line changes.

Worth naming: the Mem0 PAPER shows the same window one level up. The update phase "first retrieves the top s semantically similar memories ... These retrieved memories, along with the candidate fact, are then presented to the LLM" which picks ADD/UPDATE/DELETE/NOOP (../papers/mem0-scalable-long-term-memory.pdf, p. 4, sect 2.1). The snapshot precedes an LLM round-trip; every consolidation built on this pattern, RFA's included (src/consolidate.ts RECONCILE_SYSTEM), has a candidate set that is stale by the time its verdict lands. Single-flight consolidation per agent is what makes that harmless; recommendation 6 makes single-flight a mechanism instead of a hope.

**The gate-before-reconciliation ordering is MemClaw's second live finding, measured.** MemClaw's contradiction experiment: "The 0.490 ceiling is set by write admission: 206/400 writes were rejected 409 by the synchronous dedup gate before reaching the (post-commit) detector ... partly the genuine dedup-pre-empts-contradiction effect (a contradiction phrased as 'X is A' vs 'X is B' is near-identical text)"; conditional on both writes being admitted, supersession was correct 90/90 (../papers/governed-shared-memory-multi-agent.pdf, p. 11, sect 8.4). A contradiction and a near-duplicate look identical to a similarity gate. RFA's MemoryGate sits at both memory doors (file writes, src/memoryfs.ts:47-53; fact writes, src/memoryfs.ts:354-357), and at the facts door a rejection is a silent `"skipped"`: a peer's correction that resembles recent peer traffic (which corrections definitionally do) never reaches the reconciliation step whose whole job is contradiction handling. That is not hypothetical under concurrency; it is the design today. Recommendation 5 keeps the gate (the worm defense stands) but makes its skips observable to consolidation.

**Parallel conversations turn the model's own memory edits into multi-writer rethink.** Under rung 2, two conversations of one agent can both call `strReplace` or `insert` on `MEMORY.md` or a core block in overlapping turns. Letta's table says which verbs survive that and which do not (sect 2 above); RFA's current surface has one verb accidentally safe, two unsafe, and no owner. Recommendations 2 and 3 are the two halves of the fix: preconditions on the verbs, ownership for the heavy ones.

**MIRIX is the existence proof that multi-writer means ownership, not locking.** Six memory types are managed by "six Memory Managers for six memory components, and a Meta Memory Manager responsible for task routing" (../papers/mirix-multi-agent-memory.pdf, p. 2), reaching 85.38% on LOCOMO (p. 3). Multiple concurrent writers over one store, made safe by routing each write to the single manager that owns its type. Every scaled system in this survey lands on some form of one-writer-per-key: Letta per block, Graphiti per group_id, MIRIX per memory type, Orleans per activation ("Actor activations are single threaded and do work in chunks, called turns ... each activation always executes one turn at a time", with scale-out reserved for actors with "no state reconciliation between different activations", ../papers/orleans-virtual-actors.pdf, pp. 3-4, sect 2.1 and 2.5). The ladder's rung 6 (ownership over locking, partition at assignment) is the right instinct; the amendment is that the same principle must reach INSIDE the agent, down to memory files and blocks, not just across board tasks.

**A-Mem shows why "just parallelize the adds" is worse than it looks for linked memories.** A-Mem's mechanism is that every new memory "can trigger updates to the contextual representations and attributes of existing historical memories" (link generation plus memory evolution, ../papers/a-mem-agentic-memory.pdf, p. 2). An add is not an append; its write set includes its neighbors. Any memory design with evolution semantics (RFA's UPDATE/DELETE reconciliation qualifies) has overlapping write sets between concurrent adds, which is exactly what makes append-only episodes the correct concurrent-facing layer and everything above it single-writer.

## 4. Poisoning, amplified by concurrency

MINJA (NeurIPS 2025) establishes the write path an attacker already has: "MINJA achieves a high average success rate of 98.2% for injecting malicious records into the memory, and a high average attack success rate of 76.8%" across three agents and four victim-target pair types, via queries alone, no memory access, using bridging steps, an indication prompt, and "a progressive shortening strategy to gradually remove the indication prompt" (../papers/minja-memory-injection-attack.pdf, p. 2). The mechanism that defeats detection is making each stored record individually plausible, which is precisely the blind spot of a similarity gate.

The 2026 follow-up (a COMPSCI 690F course research report, weight it accordingly) adds two useful empirical points: realistic pre-existing legitimate memories "dramatically reduce attack effectiveness" (dilution is a real defense), and "effective memory sanitization requires careful trust threshold calibration to prevent both overly conservative rejection (blocking all entries) and insufficient filtering (missing subtle attacks)" (../papers/memory-poisoning-attack-defense.pdf, pp. 1, 3). That trade-off is MemoryGate's exact dial, and section 3 showed what over-rejection costs (contradiction starvation).

What concurrency changes: parallel conversations multiply write attempts per unit time (MINJA needs a sequence of injected records; N lanes means N sequences in the time of one), and interleaved provenance makes post-hoc forensics harder unless writes carry their origin. RFA's defenses in depth already exist at the facts layer (`source_origin` trust tiers, episode ids, the gate); the /memories file layer has only the gate. Recommendation 7 (per-write provenance on files) is the cheap concurrency-proofing: MemClaw's live eval showed full provenance chains reconstruct with writer identity intact (completeness, accuracy, depth-fidelity all 1.00, ../papers/governed-shared-memory-multi-agent.pdf, p. 9, Table 2), and Collaborative Memory's design argument is that fragment-level immutable provenance (contributing agents, resources, timestamps) is what makes "retrospective permission checks", audit and revocation possible at all (../papers/collaborative-memory-access-control.pdf, pp. 1, 3). The parallel worth stealing: RFA facts carry provenance because consolidation writes them; /memories files carry none because the model writes them. The writer that is easiest to manipulate is the one with the least provenance.

## 5. Replica reconvergence: nobody ships it; here is what research says it would take

The survey found no production system that merges two diverged agent-memory replicas. The shipped patterns are avoidance: one shared store (Letta blocks, MemClaw's service), partition (Graphiti group_ids), ownership (sleep-time, MIRIX managers), deferral (LangMem, ChatGPT). Orleans, the strongest scale proof for serialize-per-identity, explicitly reserves multi-activation for state that needs no reconciliation (../papers/orleans-virtual-actors.pdf, p. 3). The ladder's postscript (replicas as distinct members, diverging memories) therefore has zero prior art to copy, which is a finding, not a gap in the search.

The research frontier, if the trigger ever fires:

- **StateFuse** (HKU, arXiv 2607.05844, July 2026) is the most complete design. Substrate: standard OpSet/CRDT set-union merge over immutable operations ("Replica merge is still plain set union", p. 6). Contract on top: materialization emits "explicit ConflictSet objects for functional predicates with multiple distinct active values" (p. 6); resolvers act only at projection time and "may choose among surfaced candidates or abstain, but they cannot rewrite replicated state" (p. 2); corrections target an exact `claim_id` or a semantic `claim_ref` that catches "later-arriving claims" (p. 6), which solves the you-cannot-name-the-other-replica's-row problem RFA would hit. Its measured claim is deliberately narrow and worth quoting as the ceiling: "StateFuse is best supported as a safer public memory contract for contradiction surfacing, abstention, and auditable correction, not as a universal accuracy gain" (p. 1); on the benchmark, conflict-preserving surfaces tie collapsed ones on accuracy and differ in that they surface contradictions at all (p. 2). Merge does not make answers better; it makes disagreement visible instead of silently lost. That is the honest budget for recommendation 9.
- **RFA's facts layer is already half-built for this.** The columns `created_at`/`expired_at` (transaction time) and `valid_at`/`invalid_at` (event time) with DELETE-as-invalidation (src/memoryfs.ts:200-213, 347-350) copy Zep's bi-temporal edge model: "the system tracks four timestamps ... When the system identifies temporally overlapping contradictions, it invalidates the affected edges by setting their t_invalid to the t_valid of the invalidating edge" (../papers/zep-temporal-knowledge-graph.pdf, p. 3, sect 2.2.3). Close-not-delete is what makes contradiction handling order-tolerant: a late-arriving fact from replica B closes rather than deletes, so ingestion order between replicas does not change the surviving history, only which rows are open. A future two-log merge (union episodes by content hash, re-run reconciliation over the merged tail) is tractable HERE, and only here.
- **The /memories file layer is not mergeable and should not pretend to be.** Files carry no provenance (rec 7), no operation log, and their edit verbs are rewrite-shaped. Letta's own table calls whole-block rewrite last-writer-wins with lost updates; the honest replica story for files is Orleans stateless-worker discipline: replicas that write /memories are outside the model until an owner is designated per file or the layer gains an op log.
- Mem0's non-concurrent history is the warning about sequencing this work: issue #4896 documented ADD-only extraction storing contradictory facts side by side with only MD5 exact-hash dedup ("Both memories remain in storage. Search returns both", https://github.com/mem0ai/mem0/issues/4896, filed 2026-04-20, closed, fetched 2026-08-25). Consolidation quality collapses before concurrency is even involved; adding writers to a weak reconciliation loop multiplies garbage. Any concurrency rung that touches memory must pass the parity gate twice and the eval suite, exactly as CLAUDE.md already requires for memory changes.

## 6. Where this leaves the ladder

Validated: rung 2's line (parallel across conversations, serial within one) is what Letta ships and documents; rung 3 (read-only packs parallelize freely) holds for workspace but see rec 8; rung 6's ownership-over-locking is the industry consensus extended one level down.

Attacked: rung 0 is wrong as stated, because the memory surface is universal across packs regardless of posture (rec 8). Rung 1 is under-specified: an in-process lock neither fixes the verbs' semantics for the model (which needs fail-and-reread, not wait-and-clobber) nor covers the cross-process writers that exist today (recs 1, 2, 6). The ladder has no rung for pipeline ordering (rec 5) and none for provenance (rec 7), and both are cheaper than most of what it does contain. The replica postscript ("works today with zero new mechanics but diverging memories") is true and should carry a warning label: diverging memories have no reconvergence story anywhere in industry, so divergence is a one-way door until rec 9's trigger is honored.

## What this dimension could not verify

The OpenAI Memory FAQ returned HTTP 403 to direct fetch on 2026-08-25; its content was confirmed only via search-engine snapshots and the surrounding help-center pages, so the claim "no documented concurrency contract" rests on absence of evidence across those secondary views, not on a read of the live page. The Letta per-verb concurrency table was read through a doc-page fetch that flagged its own uncertainty on the memory_insert row ("Yes (concurrent-safe?)"); the direction is clear but the exact table wording should be re-checked before quoting it in a spec. Graphiti's "episodes must be awaited sequentially within a group_id" rule is asserted by Zep-adjacent docs and the MCP server's per-group queue design, but the core README no longer states it explicitly; the load-bearing version of the claim here rests on issue #1331 and the bulk-ingestion caveat instead. The memory-poisoning defense paper is a university course project report (COMPSCI 690F, Fall 2025), not peer-reviewed; it is cited only for directional findings. StateFuse and MemClaw are 2026 arXiv preprints with reference implementations; neither names an external production deployment beyond MemClaw's own memclaw.net service, whose live-eval traces are committed but not independently reproduced here. Finally, no benchmark exists that measures an agent fleet's memory quality under genuinely concurrent writes; every number cited (LOCOMO, MemoryAgentBench, ArgusFleet) is either single-writer or synthetic-concurrent, so "serialize is enough at agent scale" is supported by architecture evidence and absence of counterexamples, not by a load test.
