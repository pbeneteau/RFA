# 05-runtime-models: Actor runtimes and orchestrators - turn-based concurrency, reentrancy, session semantics

Wave 05, dimension 05. Written 2026-08-25.
Premise: RFA's turn lock plus per-conversation session keying is a rediscovery of turn-based actor concurrency; the mature actor runtimes have already paid for the answers to reentrancy, ordering, affinity and replica questions the design ladder leaves open. Repo read at commit 50f538d.
All web sources fetched 2026-08-25. The Orleans paper was downloaded to `../papers/orleans-virtual-actors.pdf` and read at page level.

## Verdict

**RFA's turn lock is the Orleans default (single-threaded, non-reentrant activation) with the Orleans failure mode included for free: a call cycle deadlocks until a timer kills it, and today RFA detects the A asks A and A asks B asks B asks A cycles only by the reply_by clock, 120 seconds of dead air by default. The mature runtimes split cleanly on the cure. Orleans and Dapr ship chain-id reentrancy (admit a call only if it carries the id of the chain you are blocked on), Swift makes actors fully reentrant and accepts broken invariants across every await, Erlang/OTP fails self-calls fast at the call site and leaves mutual cycles to convention, and Akka says do not block at all: model the reply as a message. For RFA the interleaving cures are unavailable at the conversation level, because the mutable state of a model turn is the SDK session transcript, and the field evidence is unambiguous that one Claude session id must have at most one writer (JSONL branch forking with stale-branch anchoring, and mid-write corruption that crashes the CLI). What transplants cheaply is the detection half of the Dapr/Orleans design: propagate a call-chain id on every ask and refuse a cycle immediately instead of letting the clock expire, plus a depth cap. What the ladder gets factually wrong: SDK sessions CAN fork (forkSession creates a new id seeded with the history, tail-only, no merge primitive), and what it misses entirely: nested synchronous asks hold account leases down the whole chain, so any chain deeper than the account cap deadlocks the whole account with zero cycles involved, and the effective default cap is 2, not 3: `agents.max_inflight` defaults to 2 in the rfa.json schema (src/hubdir.ts:65) and the supervisor writes that value as the cap (src/supervisor.ts:111, 665), while DEFAULT_CAP 3 (src/account.ts:43) applies only when no supervisor has ever set a cap. A chain of depth 2 already freezes a default account. Temporal independently validates rung 2 (serial per workflow execution, parallel across executions) and supplies the crash-recovery pattern rung 6 lacks (sticky queue, 5 second fallback, replay from history), and RFA already persists the exact replay anchor it would need: `{claude_session_id, room_cursor}`.**

## 1. What RFA actually does today (repo, commit 50f538d)

- One process, one turn: `makeTurnLock()` is a FIFO promise chain (src/turnlock.ts:15-28); every brain caller goes through it (src/resident.ts:550-553). No priority, no fairness classes.
- The serve loop is doubly serial: `serve()` awaits the handler inline before it even listens again (src/client.ts:381-411). During a model turn, new requests are not just queued behind the turn lock, they are unread.
- The self-call/cycle deadlock is real and clock-bounded: the roster `ask_<member>__<skill>` tools call `this.ask()` from inside the model turn (src/client.ts:462-477); `ask()` defaults to `timeoutMs 120_000` and stamps `reply_by` from it (src/client.ts:295-302), and the only exits are the reply, the hub's `timeout` system event, or `gone_quiet` (src/client.ts:326-331). If A's turn asks A, the request sits unread until A's turn dies on the clock. Same for A asks B asks A: both sides burn their full window. This is byte-for-byte Orleans "Case 2: the calls deadlock ... Orleans determines that the call has timed out, and each call results in an exception" (https://learn.microsoft.com/en-us/dotnet/orleans/grains/request-scheduling).
- Sessions are keyed per conversation and resumed per turn: `resume: sessions.get(convoKey)` then `sessions.set(convoKey, msg.session_id)` (src/resident.ts:687, 699). The turn lock is currently the only thing preventing two turns from resuming one session id.
- The account cap is a lease held for the whole turn: `account.waitForSlot(..., { timeoutMs: 120_000 })` before the query, `currentLease` held until completion (src/resident.ts:575-577). A turn blocked inside an ask keeps its lease. The cap that matters in practice is 2: `agents.max_inflight` defaults to 2 in the rfa.json schema (src/hubdir.ts:65) and the supervisor writes the manifest value as the account cap (src/supervisor.ts:108-111, 665); DEFAULT_CAP 3 (src/account.ts:43) is only the fallback when no supervisor has ever written a cap.
- A checkpoint `{claude_session_id, room_cursor}` is already persisted per run (src/resident.ts:860, 1065).

## 2. Orleans: the closest prior art, read from the paper and the shipped fix

Paper: Bernstein, Bykov, Geller, Kliot, Thelin, "Orleans: Distributed Virtual Actors for Programmability and Scalability", MSR-TR-2014-41 (../papers/orleans-virtual-actors.pdf, 13 pages, read 2026-08-25).

What the paper establishes, page-level:

- Turns, defined (p.4, sect 2.5): "Actor activations are single threaded and do work in chunks, called turns. An activation executes one turn at a time." Interleaving is opt-in via `[Reentrant]`, and even then "execution of turns of both requests is still guaranteed to be single threaded". Reentrancy in Orleans is interleaving at await points, never parallelism. RFA's turn lock is the non-reentrant default of this model.
- Single activation is enforced by a directory, not by luck (p.5, sect 3.2): registration of a second activation of a single-activation actor is rejected and the existing address returned. RFA's analog is the hub roster plus one resident process per pack; a multi-replica RFA needs an equivalent authority (the task board claim with a resource key, ladder rung 6, is that directory).
- Eventual single activation (p.7, sect 3.9): during membership flux Orleans tolerates duplicate activations and later drops one, having "made this tradeoff in favor of availability"; applications needing stronger consistency must rely on external persistent storage. Direct read-across: an RFA replica takeover WILL occasionally overlap with a not-yet-dead owner; the design must make a duplicate-turn window survivable (idempotent effects, fencing tokens on the board) rather than pretend it cannot happen.
- Stateless worker mode (p.3, sect 2.1, facet 4): many activations of one actor are allowed only where there is "no state reconciliation between different activations", so the mode "is appropriate for actors with immutable or no state, such as an actor that acts as a read-only cache". This is the strongest prior-art statement on the ladder's replicas-as-distinct-members postscript: replicas that write memory and never reconcile are outside what Orleans was willing to ship. Recommendation 7.
- Production scale for the model (p.10-11, sect 5.2): Halo 4 Presence at 25 servers sustained about 130,000 heartbeats/s, scaling near-linearly to 125 servers; median latency 6.5 ms at 19% CPU. Turn-based concurrency is not the bottleneck at six orders of magnitude above RFA's load.

The deadlock fix Orleans actually shipped, and its price:

- Mechanism (PR #7770, merged for Orleans 7): a `CallChainId` is propagated with each request; "when determining if a call can interleave on a grain, we examine the current blocking request (each activation has at most one) and if its CallChainId matches the incoming request's CallChainId, then we allow it to interleave" (https://github.com/dotnet/orleans/pull/7770). Only the blocking request is considered; background calls are not.
- Cost (PR #8023): "The Call Chain Reentrancy feature uses an AsyncLocal (via RequestContext) which can hurt performance by around 20% in some scenarios", so it became opt-in per chain via `using var _ = RequestContext.AllowCallChainReentrancy();` (https://github.com/dotnet/orleans/pull/8023, API: https://learn.microsoft.com/en-us/dotnet/api/orleans.runtime.requestcontext.allowcallchainreentrancy?view=orleans-8.0). A mature runtime with ten years of production behind it measured a 20% tax just for tracking the chain, and made the deadlock cure something you must ask for.
- The full ladder of interleaving controls (request-scheduling doc): `[Reentrant]` (class), `[AlwaysInterleave]` (method), `[ReadOnly]` (concurrent with other ReadOnly), `[MayInterleave]` (predicate), `AllowCallChainReentrancy` (call site). RFA's posture system (declared tools) is a coarse `[ReadOnly]`: rung 3 (read-only packs parallelize freely) is the same judgment Orleans encodes per method.

Why the interleaving half does not transplant: an Orleans grain admits the re-entering call by running its turns interleaved on the shared in-memory state. RFA's equivalent shared state for a conversation is the SDK session transcript, and section 5 below shows one session id tolerates exactly one writer. Chain-id ADMISSION is unavailable; chain-id DETECTION is not, and detection alone converts a 120 second silent deadlock into an instant refusal the calling model can react to inside its own turn. That is recommendation 1, and it is the Dapr shape, not the Orleans shape.

## 3. Dapr, Swift, Erlang, Akka: the full option space

- Dapr actors: per-actor lock per turn (https://docs.dapr.io/developing-applications/building-blocks/actors/actors-features-concepts/); opt-in reentrancy matches "requests from the same chain, or context" by a propagated `Dapr-Reentrancy-Id` header, with `maxStackDepth` defaulting to 32 (https://docs.dapr.io/developing-applications/building-blocks/actors/actor-reentrancy/). This is the simplest complete design: an id, a header, a depth cap. RFA needs only the refusal variant of it.
- Swift SE-0306 chose the opposite pole: actors are reentrant by default because "reentrancy by default all but eliminates the potential for deadlocks", at the documented price that every await is a point where actor state may have changed under you (https://github.com/swiftlang/swift-evolution/blob/main/proposals/0306-actors.md). This is the best-argued counter-position to RFA's lock, and it loses here for the same session-transcript reason: Swift's interleaving damage is "invariants must hold at every await"; an LLM agent cannot even express that discipline over a transcript.
- Erlang/OTP: raw processes dodge some of this with selective receive, and the compiler makes ref-tagged receives skip the whole prior mailbox: "it will tell the emulator to search only the messages that arrived after the call to monitor/2" (https://www.erlang.org/doc/system/eff_guide_processes.html). But the gen_server framework layer serializes turns again, and OTP's answer to self-call is fail-fast at the call site: `gen_server:call` exits with reason `calling_self`, documented as "A call to self/0 would hang indefinitely" (https://www.erlang.org/doc/apps/stdlib/gen_server.html). Mutual cycles between two servers still deadlock until the 5 s call timeout, and the ecosystem's cure is convention (never call your own public API from a callback; prefer cast). Twenty-five years in, the most battle-tested actor runtime never mechanized the cross-process cycle case; it mechanized only the self-call, which is the cheap 80%. RFA can do both for the same price because the chain id rides the envelope.
- Akka: the idiom is that blocking on Ask inside an actor is the bug, not the cycle; Akka.NET #2546 showed even the framework's own continuation scheduling could block the dispatcher worker ("user code runs on (and blocks) the Helios worker thread"), fixed at framework level with `RunContinuationsAsynchronously` (https://github.com/akkadotnet/akka.net/issues/2546). The community rule "don't ask, tell" models the reply as a plain message handled in a later turn, so an actor is never suspended mid-turn. Applied to RFA this is recommendation 3: the deep fix for nested asks is not admitting re-entry, it is ending the turn and continuing on reply. It costs continuation state (which turn was waiting for what, resumable after restart), which is why it is parked rather than decided.

## 4. Temporal and Ray: keyed serialization, affinity, and the price of concurrency

- Temporal serializes workflow tasks per workflow execution while running unbounded executions in parallel across a task queue: the sticky-queue arch doc and sticky execution page describe one workflow task at a time per execution, cached on an owning worker. This is rung 2 exactly, shipped at industrial scale: parallel across conversations, serial within one.
- Sticky execution is the missing crash-recovery rung: the owning worker polls a private sticky queue; "if the Worker fails to start a Workflow Task in the Sticky Queue shortly after it's scheduled (within five seconds by default), the Temporal Service disables stickiness for that Workflow Execution" and the task goes back to the shared queue for full-history replay on any worker (https://docs.temporal.io/sticky-execution). The pattern is affinity as an optimization, replay as the source of truth. RFA already persists the replay anchor per run, `checkpoint: { claude_session_id, room_cursor }` (src/resident.ts:1065); what a takeover needs is the session file on the new host, which the Agent SDK now covers with the SessionStore adapter or by moving the JSONL (https://code.claude.com/docs/en/agent-sdk/sessions, "Resume across hosts"). Recommendation 8.
- Temporal's concurrency dial is slots, and the current docs say fixed slot counts are being superseded by resource-based slot suppliers that hand out slots from live CPU/memory targets, with the honest caveat that targets can be exceeded because "resources consumed during a task can't be known ahead of time" (https://docs.temporal.io/develop/worker-performance). RFA's `max_inflight = 3` is the fixed-count generation of this design; fine for now, but the lease-held-while-blocked defect (recommendation 4) must be fixed before any adaptive tuning is worth discussing.
- Ray states the ordering price of intra-actor concurrency in one sentence: "Asynchronous or threaded actors do not guarantee the task execution order", even from the same submitter (https://docs.ray.io/en/latest/ray-core/actors/task-orders.html). Rung 0's `concurrency: N` buys this loss and the ladder does not say so. Recommendation 6.
- Ray concurrency groups are per-lane caps inside one identity: named groups each with their own concurrency ("io" at 2, "compute" at 4, a default group at 1000 for async actors, 1 otherwise; https://docs.ray.io/en/latest/ray-core/actors/concurrency_group_api.html). This is the shape for RFA lanes if the FIFO turn lock ever needs priority classes (recommendation 9). At the account layer lanes already carry real per-lane admission ceilings: RESERVE { serve: 0, schedule: 1, background: 2 } (src/account.ts:40) and laneLimit() (src/account.ts:216-219) give each lane a ceiling of cap minus its reserve, so serve may fill the cap, schedule must leave one slot free and background two ("priority without a scheduler", src/account.ts:34-39). What has no priority is the in-process turn lock, plain FIFO (src/turnlock.ts:15-28), and that lock is where the recommendation-9 inversion lives.

## 5. Claude Agent SDK sessions: what fork actually is, and what concurrent resume actually does

The ladder's rung 2 parenthetical "SDK sessions cannot fork" is wrong, and the correction matters because it changes which designs are possible.

- Fork exists and is documented: `resume` plus `forkSession: true` (TS) / `fork_session=True` (Python) "creates a new session that starts with a copy of the original's history but diverges from that point. The fork gets its own session ID; the original's ID and history stay unchanged" (https://code.claude.com/docs/en/agent-sdk/sessions, fetched 2026-08-25). Fork branches conversation history only, never the filesystem (the docs say so explicitly; file checkpointing is the separate mechanism).
- Fork granularity is session-tail only: forking from an arbitrary earlier message (`resume_at` by message UUID) is a feature request, closed as duplicate of the `resume_from_turn` proposal, both unshipped (https://github.com/anthropics/claude-agent-sdk-python/issues/690). There is also no merge primitive in either direction: two forks reconverge only by app-level summarization into a new prompt.
- Concurrent resume of ONE session id without forking is corruption, not contention. Two independent failure classes are on record. Structural: concurrent `--resume` processes fork the JSONL into a tree of branches, and the resume leaf-picker then "consistently anchors to a stale branch"; every new message "gets appended as a child of that stale leaf ... after several cycles the tree accumulates hundreds of short branches, none connected to the real conversation tip" (real transcript: 3,356 entries, 375 leaves; https://github.com/anthropics/claude-code/issues/48270, closed not-planned, i.e. the behavior stands). Physical: interleaved writers truncate lines mid-write ("truncated and out-of-order JSON lines"), and the corrupted transcript crashes the CLI with `RangeError: Maximum call stack size exceeded` (https://github.com/anthropics/claude-code/issues/20992).
- The docs never claim concurrent resume of one id is safe, and the issue tracker shows it is not. So the load-bearing invariant for every rung of the ladder is: at most one live writer per session id. Rung 2 keyed serialization is therefore correct for the wrong stated reason; restated properly (recommendation 5): serialize turns per conversation key because the conversation key owns a session id, and fork when a conversation genuinely needs parallel branches, accepting tail-only granularity and no merge.
- The fan-out warning from the most popular agent framework: LangGraph's parallel Send execution against a shared checkpointer lost conversation memory across turns ("when i m asking the follow up question its not able to recognise the history"), closed without a clear fix (https://github.com/langchain-ai/langgraph/issues/3380). Parallel branches plus one shared conversation state is a live bug source even where the framework was designed for it.

## 6. Where the ladder is attacked, summarized

1. Missing rung: reentrancy. The ladder has no answer for A asks A or A asks B asks A. Today both deadlock unread (section 1) until reply_by. Every runtime surveyed treats this as a first-class design decision, not an edge case. Cheapest correct transplant: Dapr-style chain id plus depth cap, refusal not admission (recommendation 1). The expensive correct transplant, turn-splitting continuations, is parked with a named trigger (recommendation 3).
2. Missing rung: lease starvation. Nested asks hold account leases while blocked. Chain depth >= the cap freezes the whole account for up to 120 s per level, no cycle required (src/resident.ts:575-577 plus src/client.ts:295), and the default cap is 2 (`agents.max_inflight`, src/hubdir.ts:65, written by the supervisor at src/supervisor.ts:111, 665; DEFAULT_CAP 3 in src/account.ts:43 is only the no-supervisor fallback), which strengthens the finding: a chain of depth 2 already freezes a default account. This is the classic blocked-thread-pool deadlock that Orleans avoids by releasing the thread at every await and Temporal avoids by making slots cover execution, not waiting. Recommendation 4.
3. Wrong premise in rung 2: sessions do fork. The rung's conclusion survives on corrected grounds (one writer per session id), and gains a tool: fork-per-branch for intentional parallel exploration of one conversation. Recommendation 5.
4. Silent cost in rung 0: `concurrency: N` abandons per-sender ordering unless per-conversation FIFO is preserved explicitly. Ray states this price in its docs; RFA should too. Recommendation 6.
5. The replicas postscript is more dangerous than it reads: Orleans restricts unreconciled multi-activation to stateless/read-only actors by design, and its own eventual-consistency section admits duplicate activations happen during flux. Diverging memories on writing replicas is not a quirk to note, it is the reason the mode should be posture-gated. Recommendations 7 and 8.
6. The turn lock has no fairness story: FIFO admits priority inversion between lanes (a due consolidation ahead of a waiting human). Prior art (Ray groups) exists; parked until it hurts measurably. Recommendation 9.

## What this dimension could not verify

The Orleans ~20% AsyncLocal regression is the PR author's characterization ("in some scenarios") with no published benchmark methodology; treat it as an order of magnitude, not a number. The Temporal Go SDK's historical default of 1000 for `MaxConcurrentActivityExecutionSize` could not be confirmed on the current worker-performance page (the page now steers to slot suppliers and prints no defaults), so no default is claimed in this note. The LangGraph issue #3380 is a user report closed without a maintainer root-cause; it evidences the bug class (fan-out plus shared checkpoint state), not a specific LangGraph defect that persists today. Whether the Claude Code stale-branch anchoring in issue #48270 has since been changed in newer CLI versions is unknown (closed not-planned as of the 2026-08-25 fetch); the one-writer-per-session-id rule does not depend on it, since the mid-write corruption class (#20992) is independent. Finally, the claim that the hub emits a `timeout` system event at reply_by was verified only from the client's consumption side (src/client.ts:326); the hub emission path was not re-read for this note.
