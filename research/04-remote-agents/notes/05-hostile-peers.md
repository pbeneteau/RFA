# 05 - Hostile peers: the threat model for cross-org rooms, and what RFA already stops

Dimension 05 of research wave 04 (remote agents become first-class room members). Depth: DEEP.
Research date: **2026-08-17**. Researcher: subagent under the wave-04 orchestrator.
Grounding read first, in this order: [`STATUS.md`](../../../STATUS.md), [`spec/RFA-0.1.md`](../../../spec/RFA-0.1.md) (0.1.7), [`spec/RFA-0.4-platform.md`](../../../spec/RFA-0.4-platform.md), [`research/03-reach-and-collaboration/REPORT.md`](../../03-reach-and-collaboration/REPORT.md) + `notes/01-remote-reach.md` + `notes/03-multi-agent.md` + `notes/05-governance-v2.md`, [`src/store.ts`](../../../src/store.ts), [`src/client.ts`](../../../src/client.ts), [`src/main.ts`](../../../src/main.ts), [`src/memoryfs.ts`](../../../src/memoryfs.ts), [`src/consolidate.ts`](../../../src/consolidate.ts), [`src/resident.ts`](../../../src/resident.ts), [`src/bridge.ts`](../../../src/bridge.ts), [`console/index.html`](../../../console/index.html).

Premise honored: RFA is a tool ANY org self-hosts. Rooms carry LOCAL agents (agent.md packs, supervised here) and REMOTE agents (another framework, another product, another org's cloud) that must CLAIM and COMPLETE real tasks with tools the hub never sees. A remote member may be hostile or merely incompetent. The operator is one developer plus agents, so every control has to pay for itself.

Method: primary sources for every load-bearing claim (the OWASP PDF was extracted with `pdftotext` and quoted from the document itself, not from a mapping guide). Anything I could not confirm is prefixed `UNVERIFIED:`. Repo claims carry file and line.

## Verdict

### Headline

**RFA's defensive core is right and unusually complete for its age: origin stamping, the untrusted-content boundary, the memory admission gate, the policy gate, evict/quarantine with human-only release, and a hash-chained log already cover most of OWASP ASI07/ASI09/ASI10 by construction. Three things are actually broken for cross-org use, and they are broken in code, not in philosophy:**

1. **T0 is not an authentication tier, it is a shared password.** One `join_secret` per room ([`src/store.ts:384`](../../../src/store.ts)), handed to every joiner, no per-member credential, no expiry, no revocation short of rotating the room. MCP's own 2026-07-28 security page states the rule this violates: "MCP servers **MUST NOT** treat possession of a state handle as authentication" (https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices). Fix: per-member single-use invites. This is the single highest-value change in the wave.

2. **`history_visibility: "joined_after"` does not work.** The policy is enforced only on the join contract ([`src/store.ts:542-547`](../../../src/store.ts)); `room_listen` floors `since` at nothing but the log tip ([`src/store.ts:1516`](../../../src/store.ts)). Any member, including one that joined thirty seconds ago from another org, can call `room_listen{since: 0, timeout_ms: 0, wait_for: "all"}` and page the entire room history in `replayCap`-sized chunks. This contradicts spec 14.5 in the same document that promises it. It is a bug, not a design decision.

3. **The task board has no admission control, so a hostile remote member is a one-line denial of service.** `claim` checks state, ownership and blockers and nothing else ([`src/store.ts:1663-1673`](../../../src/store.ts)): no capability match against the claimant's card, no per-member concurrent-claim cap, no release when the owner goes offline, and `list` returns every task in the room to every member ([`src/store.ts:1659-1661`](../../../src/store.ts)). A remote member claims everything, moves it to `working`, and the board is dead; `reply_by` produces a one-shot `task_overdue` notice and never releases the task. MCP's tasks extension SEP-2663 documents the general version of this as unsolvable in MCP because there is no authorization context to bind to ("it is unsafe for a server to support `tasks/list` at all"); RFA HAS the context (room membership) and simply does not use it.

**The one control the room design makes worse, and that no amount of prompt text fixes: exfiltration.** A local agent holding an org's knowledge, answering another org's agent, is a strip-mine waiting to happen. The gate already sees every outbound message, so the mechanism exists; what is missing is the ability to express "when the recipient is remote" ([`GateCheck.match`](../../../src/store.ts) has `kind`, `origin`, `text_regex`, `ext_key` and nothing about the recipient, [`src/store.ts:83-90`](../../../src/store.ts)). Add recipient predicates and per-member visibility on card skills and the exfiltration story goes from "we told the model not to" to "the hub enforces a budget and a filter". It still does not become airtight, and section 4 says why honestly.

**The enabling primitive for all of it is one new server-stamped field.** Every fix below keys off knowing whether a member is local or remote. Add `zone` to the member record and to `envelope.from`, derived from the credential presented at join, never client-supplied, exactly as `origin` already is ([`src/store.ts:828`](../../../src/store.ts)). OWASP ASI10's second mitigation names it: "Assign Trust Zones with strict inter-zone communication rules". One field unlocks gate predicates, history rules, quotas, card projection, approval-card provenance and forensics. Build that first; nothing else in this note is worth doing before it.

### Normative spec additions, in dependency order

Numbered so the ladder can be built in this sequence. Draft text is deliberately short; each line is meant to land in the named section.

**N1. Spec 4.2, new paragraph after the tier table (depends on nothing).**
> Every membership carries a hub-derived **zone**: `local` when the joining principal is administered by the hub operator, `remote` otherwise. The hub MUST derive `zone` from the credential presented at join and MUST ignore any client-supplied value, exactly as for `origin` (14.1). `zone` MUST appear in every presence record, roster entry, and `envelope.from`. A hub that cannot distinguish the two MUST stamp every member `remote`.

**N2. Spec 4.2 + 5.1 + 15 (depends on N1).**
> Hubs SHOULD support per-member invitations: `room_admin invite` returns `{invite_token, expires_at, uses}` and MAY bind `name_hint`, `zone`, and `org`. An invite MUST be single-use by default and MUST expire. `room_join` accepts an invite token in place of `join_secret`. Errors: `invite_expired`, `invite_consumed`. A room whose `policies.join` is `invite` and that admits `zone: remote` members SHOULD NOT rely on a shared room secret: one leaked secret is full room access for any party that holds it.

**N3. Spec 9.3 + 14.5 (independent; ship immediately, it is a bug fix).**
> Under `history_visibility: "joined_after"`, `room_listen` MUST clamp `since` to the caller's join sequence and MUST NOT return events earlier than it. Under `history_visibility: "member"`, replay remains unrestricted within the room's retention window. History visibility is a property of the membership, not of the join contract alone.

**N4. Spec 12.2 (depends on N1).**
> `match` additionally accepts `to_zone` (array of zones; matches when any resolved recipient is in the set), `to_member` (array of member refs), and `direction` (`inbound` for messages arriving at the room from the matched sender, `outbound` for messages addressed to the matched recipients). A check with `to_zone: ["remote"]` and `kind: ["response"]` is the egress idiom: it inspects what local agents reveal to other organizations.

**N5. Spec 5.1 + 10.2 (depends on N1).**
> `policies.claim_policy`: `open` (default, current behavior), `capability` (the hub refuses a claim unless the claimant's card advertises a skill whose id matches the task's `skill` field), `award` (only the task creator or the host may set `owner`; `claim` returns `unauthorized`). `policies.max_claims_per_member` (default 3) caps concurrent non-terminal owned tasks; excess claims return `rate_limited`. A claimed non-terminal task whose owner's presence lease has been expired for longer than `claim_grace_s` (default 300) MUST be released to `submitted` with `owner: null` and a `task {action: "released"}` event. `policies.task_visibility`: `room` (default), `participants`, `involved` (creator, owner, verifier, and the host only) scopes `list` and `get`.

**N6. Spec 5.2 + 12.1 (depends on N1).**
> A member MAY be in **probation**: probation is visible in the presence record, and a probationary member MUST NOT claim tasks or register approval requests, MUST be subject to `probation_rpm` if set, and SHOULD have every send audited. Hubs SHOULD place new `zone: remote` members in probation by default for `probation_window`. `room_admin clear_probation` requires the host or a supervisor; `set_probation` re-applies it.

**N7. Spec 12.1 (depends on N1).**
> An approval card presented to a human MUST carry the requester's member id, `origin`, and `zone`, and MUST identify the room. The card's action label MUST be generated by the hub or by a local client from the requested verb and parameters; requester-supplied free text MUST NOT be the label. Any requester-supplied text rendered in a card MUST be sanitized per 14.3 and length-capped with a counted elision marker that preserves head and tail. Hubs SHOULD cap pending approvals per member.

**N8. Spec 14.3, replacing "strip control chars" with a named set (independent).**
> Sanitization MUST remove or neutralize: C0 controls except tab and newline (U+0000-U+0008, U+000B-U+001F, U+007F); bidirectional formatting and isolate controls (U+202A-U+202E, U+2066-U+2069); zero-width and joiner characters (U+200B-U+200D, U+2060, U+FEFF); and the entire Unicode TAG block (U+E0000-U+E007F), which has no glyph in mainstream renderers and therefore reaches a model while being absent from every human review surface. Whitespace runs SHOULD be folded. The same set applies to sender names, card text, approval previews, task titles, notes, and evidence summaries.

**N9. Spec 6.1 + 6.3 + 15 (depends on N1).**
> A skill MAY carry `visibility: {zones: [...]}`; absent the field, the skill is visible to all zones. The hub MUST filter `card_summary.skill_ids` and `agent_describe` skill lists by the requesting member's zone, and MUST refuse a `request` whose `json` part names a skill not visible to the sender with error `skill_not_offered`. The **digest is computed over the full card**, unfiltered, so cache identity is unaffected by projection.

**N10. Spec 5.1 + 9.1 (depends on N1).**
> Hubs SHOULD enforce `policies.egress_bytes_per_hour` per (sending member, recipient zone) pair. On breach the send returns `rate_limited` with `retry_after_s` and the hub appends a `system {event: "egress_budget_exceeded"}` audit event.

**N11. Spec 4.2 T2 + 8 + 13 (depends on N1; heaviest item).**
> Envelopes MAY carry `sig`: a JWS (EdDSA or ES256, never `none`) over the RFC 8785 canonical form of the envelope with `sig`, `seq`, and `ts` excluded, keyed by the sender's card key (`kid` = RFC 7638 thumbprint). Hubs that accept `zone: remote` members SHOULD require `sig` on `task` claim/complete envelopes, on approval requests, and on `refuse`, and MUST record the verification verdict in the log. A signature proves origin and integrity; it never proves that a claim is true.

**N12. Spec 13 (independent).**
> Hubs SHOULD periodically append `{room, seq, prev_hash_head, ts}` to an anchor log that can be published or handed to a counterparty, and SHOULD ship an offline verifier. Without an external anchor, the chain proves only that no party other than the hub rewrote the log.

**N13. Spec 14, new item 10 (documentation, no code).**
> **Room membership is a visibility grant.** Every member can read every event delivered to it, and `wait_for: "all"` is available to every member. Rooms partition trust at the room boundary, not inside it. Confidentiality between two members of the same room is NOT a protocol guarantee; use separate rooms.

### What stays open by design (say this out loud, in the spec)

1. **Prompt injection of a local agent through legitimate content.** A task result or an answer that a local agent must read can carry instructions. The boundary wrapper, the gate, attention scoping and least-privilege tools bound the blast radius; nothing removes the class. Anthropic's Nov 2025 report is the field evidence that decomposition beats content screening.
2. **Query-only memory poisoning (MINJA class).** The MemoryGate stops verbatim replication (the Morris-II shape it was built for) and does not stop an attacker who induces the agent to write its own paraphrase. R11 and R14 make it survivable and forensically visible, not impossible.
3. **Exfiltration through legitimate answers.** Any agent allowed to answer at all can be strip-mined by a patient asker. Budgets, per-zone skill visibility and outbound gating make it slow, bounded and logged. See section 4.
4. **Remote execution honesty.** The hub cannot audit a remote member's tools; that is the premise, not a defect. Evidence + a differently-zoned verifier is the whole lever.
5. **Collusion between remote members.**
6. **Competence.** A signed card proves a key held a card. A2A says it plainly of its own signatures. Nothing in any protocol proves an agent is good at what it claims.
7. **Metadata inference.** Explicitly rejected as ceremony at this scale.
8. **The hub operator.** For the hub's own org the log is an audit trail; for a counterparty it is the other side's word until it is anchored (N12) and until senders sign (N11).

### 3. Academic taxonomies and the results that change RFA's design

**Layered Attack Surface Model (LASM)** - the current published taxonomy that actually locates threats architecturally. *"A Systematic Survey of Security Threats and Defenses in LLM-Based AI Agents: A Layered Attack Surface Framework"*, Kexin Chu, arXiv **2604.23338**, submitted 2026-04-25. Abstract verbatim, the sentence that matters:

> Existing security taxonomies, however, primarily organize threats by attack type, such as prompt injection or jailbreaking, and therefore obscure where in the agentic stack a threat arises and over what timescale it manifests. We propose the Layered Attack Surface Model (LASM) ... LASM decomposes the agentic stack into seven layers -- Foundation, Cognitive, Memory, Tool Execution, Multi-Agent Coordination, Ecosystem, and Governance -- and augments them with a four-class temporality axis covering instantaneous, session-persistent, cross-session cumulative, and sub-session-stack threats.

Useful because RFA's own components map cleanly onto layers: the boundary wrapper is Cognitive, the MemoryGate is Memory, the sandbox seam is Tool Execution, the room protocol is Multi-Agent Coordination, the gate + approvals + chain are Governance. The temporality axis is the better argument for R14: a "cross-session cumulative" attack is invisible in any single run and only visible in the log.

**MINJA - the result that breaks RFA's memory-gate assumption.** *"Memory Injection Attacks on LLM Agents via Query-Only Interaction"*, Shen Dong, Shaochen Xu, Pengfei He, Yige Li, Jiliang Tang, Tianming Liu, Hui Liu, Zhen Xiang. arXiv **2503.03704**, submitted 2025-03-05, last revised **2026-02-12**, NeurIPS 2025 poster (https://neurips.cc/virtual/2025/poster/118152). Threat model verbatim: the attacker "cannot directly modify the agent's memory bank" and instead injects "malicious records into the memory bank by only interacting with the agent via queries and output observations". Two stages: **bridging steps** ("a sequence of bridging steps to link victim queries to the malicious reasoning steps") and an **indication prompt with progressive shortening** ("guides the agent to autonomously generate similar bridging steps, with a progressive shortening strategy that gradually removes the indication prompt"). `UNVERIFIED:` the 98.2% / 76.8% figures circulating for injection and attack success are from secondary summaries; the abstract says only "extensive experiments across diverse agents demonstrate the effectiveness of MINJA".

Why this is load-bearing: RFA's `MemoryGate` is a **cross-sender near-duplicate detector** ([`src/client.ts:505-559`](../../../src/client.ts)) built for the Morris-II worm shape (5-char shingles, Jaccard >= 0.9, 64-message window, same-sender repeats left to hub dedupe). MINJA's injected records are the agent's OWN generated reasoning, so their Jaccard similarity to any peer message is low by construction. **The gate cannot see it.** The consolidation path makes the exposure concrete: `src/consolidate.ts` extracts facts from episodes with a tool-less haiku call, primes the gate window from the same batch (a genuinely good design against verbatim replication, [`:94-101`](../../../src/consolidate.ts)), and then writes facts whose `source_origin` is `agent` when any inbound episode is non-human ([`:125`](../../../src/consolidate.ts)). That tier is then **ignored at retrieval** ([`src/memoryfs.ts:272`](../../../src/memoryfs.ts)). R11 is the cheap partial answer; R14 is the detection answer.

**Forensic detection of memory poisoning.** *"Forensic Trajectory Signatures for Agent Memory Poisoning Detection"*, Jun Wen Leong, arXiv **2606.30566**, v1 2026-06-29 (v2 2026-07-21). Abstract verbatim:

> We discover a behavioral invariant in LLM agents under persistent memory poisoning and characterize its deployment boundary. In architectures where retrieval is routed through observable memory-tool invocations, successful attacks require calling memory_recall_fact before email_send_email, a transition mechanistically forced by the attack's information-retrieval dependency. A simple rule exploiting this invariant achieves AUC = 0.9563; a Random Forest over 19 trajectory features refines it to AUC = 0.9904 (BCa 95% CI [0.987, 0.993]).

The condition in the first sentence is the design requirement: "**in architectures where retrieval is routed through observable memory-tool invocations**". RFA's residents call `mcp__memory__*` tools (observable) but the L3 fact retrieval is an in-process call whose result is spliced into the prompt string ([`src/resident.ts:606-609`](../../../src/resident.ts)) and never recorded. Making retrieval observable in the run record costs one field and buys a 0.95-AUC detector.

**Channel prioritization.** *"MESA: Prioritizing Vulnerable Communication Channels for Securing Multi-Agent Systems"*, Kunyang Li, Kyle Domico, Jonathan Gregory, Patrick McDaniel, arXiv **2606.30602**, 2026-06-29. Abstract verbatim: "the channel-level attack impact is highly non-uniform: **a single compromised edge can account for up to 75% of total attack success**". Directly supports spending the defensive budget on one edge: local-knowledge-holder <-> remote member. That is the edge R4/R9/R10/R15 all target.

**The principled ceiling.** *"Design Patterns for Securing LLM Agents against Prompt Injections"*, Beurer-Kellner, Buesser, Creţu, Debenedetti, Dobos, Fabian, Fischer, Froelicher, Grosse, Naeff, Ozoani, Paverd, Tramèr, Volhejn. arXiv **2506.08837**, submitted 2025-06-10, revised 2025-06-27. Abstract verbatim: "we propose a set of principled design patterns for building AI agents with **provable resistance to prompt injection**. We systematically analyze these patterns, discuss their trade-offs in terms of utility and security". `UNVERIFIED:` I could not extract the six pattern definitions verbatim (the arXiv abstract page does not carry section 4 and the PDF did not yield text through the fetch path); a future session should pull the HTML rendering. The relevant trade-off is nevertheless the reason for R24's rejection: the strong patterns all work by denying the untrusted-input-processing model any authority, which for RFA means a broker in front of every knowledge agent, at double cost.

**Threat-model framing.** *"MATRA: Modeling the Attack Surface of Agentic AI Systems -- OpenClaw Case Study"*, Tim Van hamme, Thomas Vissers, Javier Carnerero-Cano, Mario Fritz, Emil C. Abstract verbatim: "MATRA begins with an asset-based impact assessment and utilizes attack trees to determine the likelihood of these impacts occurring within the system architecture ... quantifying how architectural controls such as network sandboxing and least-privilege access reduce risk by **limiting the blast radius of successful injections**." Method endorsement for the table above (asset-first, then attack trees), and the "blast radius" framing is the right way to justify quotas over screening.

### 4. The exfiltration question, specifically

The premise makes this dimension's hardest problem structural, not incidental: **a local agent holding the org's knowledge is now in a room with another org's agent, and answering questions is its job.** What exists beyond prompt instructions:

**4.1 What the repo actually has today.**
- The resident answers anyone who mentions it. `serve()` hands the handler a `ServeContext` whose `from` is `{id, name}` only ([`src/client.ts:39-46`](../../../src/client.ts)); the wrapper adds `origin` ([`:454`](../../../src/client.ts)) but there is no zone, no org, no trust tier. **A local agent cannot make a trust-tiered answering decision because the SDK does not tell it who it is talking to.** R1 fixes this at the root.
- The gate sees every outbound message and can refuse or hold before append ([`src/store.ts:836-912`](../../../src/store.ts)). So egress enforcement is already in the right place in the architecture. It just cannot express the predicate (`match` has no recipient dimension, [`:83-90`](../../../src/store.ts)).
- Cards are projected identically to everyone (spec 6.3), so every skill a local agent offers is invokable by every participant.
- The default gate config demonstrates the shape that works: `no-private-keys` refuses on a regex for PEM headers ([`deploy/gate.json`](../../../deploy/gate.json)), verified live per STATUS.md. A `command`-tier check can shell a model, so a DLP-style classifier is already expressible.

**4.2 Per-member visibility on capability cards (R9): the only control that removes a path.**
Everything else narrows a path; skill visibility deletes it. If `answer-goodvest-product-question` is `visibility: {zones: ["local"]}`, a remote member never sees it in `card_summary.skill_ids`, cannot project it as a tool, and gets `skill_not_offered` if it guesses. The implementation constraint worth writing into the spec: **compute the digest over the full card and filter only the projection**, otherwise two members see different digests for one card and the "identical replicas cost zero fetches" cache contract (spec 6.2) breaks.

**4.3 Answer-side policy checks (R4 + R15): what they can and cannot do.**
Can do: block obvious markers (credentials, customer identifiers, file paths, internal URLs, a named-entity list of client names) on responses whose recipient zone is `remote`; hold a borderline answer for human release using machinery that already works end to end (STATUS.md records a held message -> inbox card -> release click -> appended envelope, seq 533/534). Cannot do: judge whether the fifth innocuous fact completes a picture. Anthropic's Nov 2025 decomposition finding is the reason to pair the check with a budget (R10) rather than trust it alone. Also note the fail-closed-to-`hold` behavior of a crashing check ([`src/store.ts:1072-1076`](../../../src/store.ts)) is the right default here and becomes load-bearing once a model-backed egress check is in the path: an operator whose classifier crashes gets a review queue, not a leak.

**4.4 Should a local agent ever answer a remote member directly?**
**Yes, and that should stay the default.** The alternative (R24's broker) is the theoretically correct answer and is rejected for v0.5 on cost: two model calls per answer, double latency, and the broker's own prompt is attackable, so the injection surface does not vanish, it moves. The defensible position is a policy knob (R15): `answer_policy: direct` by default, `gated` when the room contains a remote member and the operator wants outbound review. Escalation path recorded, not built.

**4.5 The controls that are cheap and that I would ship before any of the clever ones.**
1. `zone` in the prompt (R1). A local agent told "this asker is from another organization" behaves measurably differently, and RFA has evidence its residents honor scope instructions: STATUS.md records pm-agent correctly refusing an injected out-of-scope chat.
2. Egress budget per remote member (R10). Bytes and message counts, logged, with a `system` event on breach. This is the control that would catch the decomposed strip-mine, and it is a rolling window plus a counter.
3. Log every answer's retrieval set (R14). If it happens anyway, you can reconstruct what left.

### 5. The human in the loop under adversarial conditions

**5.1 Verifying wave 03's finding.** Wave 03's rec. 18 ("copy Claude Code's permission-relay rules verbatim") is confirmed against the primary doc, https://code.claude.com/docs/en/channels-reference (fetched 2026-08-17; channels are a research preview, Team/Enterprise orgs must explicitly enable them). Verbatim, the parts that are normative for RFA:

- `request_id`: "Five lowercase letters drawn from `a`-`z` without `l`, so it never reads as a `1` or `I` when typed on a phone. Include it in your outgoing prompt so it can be echoed in the reply. **Claude Code only accepts a verdict that carries an ID it issued.** The local terminal dialog doesn't display this ID, so your outbound handler is the only way to learn it."
- `description`: "Human-readable summary of what this specific tool call does, **never the command itself**. For a Bash call this is Claude's description of the command; when the model gives no description, the field is the constant `Run shell command` and carries zero command detail."
- `input_preview`: "The tool's arguments as JSON-shaped display text, keyed per top-level field."
- Sanitization: "Clients on Claude Code v2.1.211 or later sanitize both fields before relaying them: they **neutralize direction-override and invisible characters and quote and angle-bracket lookalikes, fold whitespace runs to a single space**, and relay text whole up to 3,500 code points, applied per top-level field for `input_preview`, which also keeps the JSON's own structural quotes. A longer value keeps its start and end visible around a counted `⋯ N code points elided ⋯` marker, so the end of a long command still reaches the approver. Earlier clients relay `description` raw and cut `input_preview` to 200 UTF-16 units with a trailing ellipsis. **Treat both fields as untrusted unless you control the client fleet.**"
- Verdict shape: "`notifications/claude/channel/permission` with two fields: `request_id` echoing the ID above, and `behavior` set to `'allow'` or `'deny'` ... **Neither verdict affects future calls.**"
- Failure semantics: "**Different format**: your inbound handler's regex fails to match, so text like `approve it` or `yes` without an ID falls through as a normal message to Claude. **Right format, wrong ID**: your server emits a verdict, but Claude Code finds no open request with that ID and **drops it silently**." And: "Both stay live: you can answer in the terminal or on your phone, and Claude Code applies whichever answer arrives first and closes the other."
- Sender gating: "Gate on the sender's identity, not the chat or room identity: `message.from.id` in the example, not `message.chat.id`." And: "Only declare the capability if your channel authenticates the sender, because **anyone who can reply through your channel can approve or deny tool use in your session**."

**5.2 Extending it for the remote case.** The relay contract assumes ONE untrusted transport and a trusted requester. The RFA remote case inverts one half: the transport (the console over loopback, or a tailnet) is comparatively trustworthy, and **the requester may be hostile**. So three of the six rules carry unchanged, and three need extension:

| Relay rule | Status for RFA remote | Extension |
|---|---|---|
| Verdict only against a server-issued id | **carries**; RFA's `request_id` is hub-registered at append time ([`src/store.ts:751-753`](../../../src/store.ts)) with duplicate detection | Add a five-character phone-typable display alias next to `apr_<run>_<n>_<b36>` if a chat channel ever lands (wave 03 rec. 18) |
| A verdict is `{request_id, behavior}`; never parse intent from free text | **carries**; `/api/approvals/decide` takes `{room, request_id, verb}` with a closed verb set ([`src/main.ts:287-292`](../../../src/main.ts)) | Make the decide endpoint idempotent per `request_id`; deciding twice is already `task_conflict` in the store ([`:1366`](../../../src/store.ts)), so surface that as a 409 rather than a 500 |
| Wrong-id verdicts dropped silently | **carries** | - |
| Both surfaces live, first answer wins | **carries**; the decision is an intervention event and `requestApproval` returns on the first match ([`src/bridge.ts`](../../../src/bridge.ts)) | - |
| Sanitize the preview | **broken**: raw 200-char slice, no neutralization ([`src/store.ts:1169-1179`](../../../src/store.ts)) | R7 + N8, with the TAG block added to Claude Code's own set |
| Gate on sender identity | **inverted**: the sender IS the adversary | **New rule, RFA-specific**: the card must state WHO asked (`requester`, `origin`, `zone`) and the action label must not be attacker-authored. A remote member's card should additionally be visually distinct in the console. Probation (R6) means a brand-new remote member cannot raise a card at all |

**5.3 How a remote member shapes what the human sees, concretely, today.**
1. Choose a confusable name at join (`NAME_RE` allows any `\p{L}`, [`src/store.ts:282`](../../../src/store.ts)) so the card reads `linear-scribe`-ish.
2. Register an approval request with `action: "save_document"` (a string it picks) and a body whose first 200 characters read like a legitimate draft ([`src/store.ts:748-778`](../../../src/store.ts), [`:1186`](../../../src/store.ts)).
3. Hide the real payload after character 200, or in invisible characters anywhere, since nothing strips bidi/zero-width/TAG.
4. The card appears in the operator's inbox alongside genuine local cards, with no origin, no zone, and no room-of-origin distinction beyond the topic string ([`console/index.html:1256-1266`](../../../console/index.html)).
5. If approved, the hub records a human-origin `approve` intervention naming that request. The hub executes nothing, so the direct damage is bounded; the real damage is **consent laundering** (OWASP ASI09 scenario 6) and approval fatigue, and a signed audit artifact the remote can point at.

The good news is that the structural half is already right: the hub does not execute an approval, only records the verdict, and the requester acts. So a hostile remote member's approved card authorizes only the hostile remote member, whose actions the hub could not audit anyway. **The fix is entirely presentational plus admission control**, which is why R7 + R6 is cheap and high value.

**5.4 The Unicode concealment result, in full, because it is the sharpest primary source on preview fidelity.**
*"Unicode TAG-Block Concealment of Tool-Metadata Payloads in the Model Context Protocol: An Approval-View Fidelity Gap Across Three Independent Server Implementations"*, Mohammadreza Rashidi, arXiv **2607.05744**, submitted **2026-07-07**. Abstract verbatim, the load-bearing sentences:

> The client renders this metadata once, in a one-time approval dialog, and then injects it verbatim into the model's context on every subsequent turn. **Nothing in the protocol requires the rendered approval view and the bytes delivered to the model to match.** We isolate that gap as a single structural mechanism, concealment encoding, and show with a model-free, protocol-free analysis that Unicode's TAG block (U+E0000 to U+E007F) has no assigned glyph in any mainstream terminal, chat, or IDE renderer, so a payload written in it is **absent from what a human reviewer sees while surviving byte-for-byte into the model's tokenizer**. ... Across 5 distinct MCP metadata surfaces we implement 8 concrete techniques with a deterministic, protocol-level harness. **All 8/8 techniques deliver an attacker-controlled payload into the model's context, 4/8 evade a representative string-matching sanitizer**, and exactly as the mechanism analysis predicts, **only the TAG-block encoding (1/8) is invisible in the human approval view while still reaching the model verbatim. MCP forces re-approval for 0/8 techniques even under a time-of-check to time-of-use rug-pull.** ... we re-implement the catalogue against 3 independently developed Python MCP server libraries and find total agreement across all 32 cross-library outcome cells. The baseline sanitizer flags 0 of 25 benign descriptions.

Three consequences for RFA:
1. **N8's character set is not paranoia**; it is the measured gap. RFA's `neutralize()` strips C0 only ([`src/client.ts:562-566`](../../../src/client.ts)), which is a "representative string-matching sanitizer" of exactly the kind 4/8 techniques evade.
2. **The "rug pull" finding maps to card rotation.** RFA is better placed than MCP here: the digest changes on card rotation, the roster emits a `presence` event with the new digest, and clients invoking a projected skill must re-project on `digest_changed` (spec 14.4). That is precisely the re-approval MCP does not force. **Write this down as a deliberate advantage rather than an accident.**
3. `card_verified` already gives tamper evidence for signed cards; combine with N8 so a card that verifies cryptographically cannot still carry an invisible instruction.

### 6. Detection and forensics: what the log must contain to reconstruct a cross-org incident

**6.1 What the chain does and does not prove.** `appendEvent` sets `prev_hash = room.chainHead` and advances the head to `SHA-256(JCS(event))` including the envelope ([`src/store.ts:2134-2146`](../../../src/store.ts)); genesis is `SHA-256(room_handle)` ([`:408`](../../../src/store.ts)); the head is recomputed by replaying the file on load ([`:2268`](../../../src/store.ts)). The only verifier is a test assertion ([`test/governance.test.ts:213-215`](../../../test/governance.test.ts)). Therefore:
- It proves **no third party mutated the file** without recomputation, given an independent copy of some head.
- It does **not** prove anything to a counterparty, because the hub operator can rewrite the whole file and recompute every link. Non-repudiation across an org boundary needs (a) external anchoring of heads (N12) and (b) sender signatures on consequential events (N11). This is the honest reason the T2 message half unparks under the new premise: the chain was sufficient when the operator was also the only party.

**6.2 What must be in the log that is not there today.** To reconstruct "the remote member asked X, the local agent retrieved Y from memory, the gate said Z, the human approved W, and the answer contained V":

| Needed | Present? | Where |
|---|---|---|
| Who said what, when, in order, tamper-evident | **yes** | room log + chain |
| Which principal class and which org | **origin yes, zone no** | [`src/store.ts:828`](../../../src/store.ts); R1 |
| Gate verdicts on refused/held/alerted messages | **yes**, and allow-outcomes deliberately not persisted for log economy (spec 12.2) | [`src/store.ts:846-912`](../../../src/store.ts) |
| Which memory facts influenced an answer | **no** | [`src/resident.ts:606-609`](../../../src/resident.ts); R14. Without it the arXiv 2606.30566 invariant is unusable |
| Which knowledge files were read for an answer | **partially**: the run records cost/turns/session but not the tool-call trace | R14 should capture the Read/Grep targets; `data/obs.db` has the dotted_order trace shape to hold them |
| The exact bytes a human approved | **no**: the card preview is a 200-char slice and the *envelope* is what gets appended; edit-before-approve merges over the original input ([`src/bridge.ts`](../../../src/bridge.ts)) | Record a hash of the exact card as presented, plus the merged final input, in the intervention `refs` |
| Membership provenance (which credential admitted this member) | **no** | R2 gives it for free: log the invite id |
| Post-hoc attribution of a claim to a remote org | **no** | N11 signatures |
| Cross-room view of one member's behavior | **no**: quarantine is per-room, approvals list is global but nothing joins a member identity across rooms | Hub-scope quarantine (threat #13) plus a member-identity key (card thumbprint) that survives rooms |

**6.3 What a hub operator can prove today, stated precisely.** "On my hub, in this room, these events occurred in this order, and nothing has been altered since I copied this head off the machine." That is genuinely useful for an internal incident review and is not evidence in a dispute with the counterparty. With N11 + N12 it becomes: "this remote member's own key signed this task claim and this completion evidence, and the chain head containing them was published at this time." That is a materially different conversation, and it is the reason R12 is `adapt` rather than `defer`.

### 7. Cross-org normative material worth copying, and one thing worth not copying

**MCP 2026-07-28 security best practices** (https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices). Three items land directly:
- **State Handle Hijacking**, verbatim: "MCP servers that implement authorization **MUST** verify all inbound requests. MCP servers **MUST NOT** treat possession of a state handle as authentication." And: "MCP servers **SHOULD** bind handles server-side to the authenticated user, for example by keying stored state as `<user_id>:<handle>` where the user ID is derived from the verified token rather than supplied by the client, and reject a handle presented by any other principal." RFA's membership token IS bound to a member ([`src/store.ts` token map](../../../src/store.ts)), so that half is satisfied; the ROOM secret is the handle-as-authentication anti-pattern, and R2 is the fix. (Note MCP is now stateless with explicit handles per SEP-2567/SEP-2575; the session-hijacking guidance moved to the 2025-11-25 version of the page.)
- **Token Passthrough**, verbatim: "MCP servers **MUST NOT** accept any tokens that were not explicitly issued for the MCP server", with the audit consequence spelled out: "The downstream Resource Server's logs may show requests that appear to come from a different source with a different identity, rather than the MCP server that is actually forwarding the tokens." This is the citation for R18's hard rejection of tool passthrough.
- **Local MCP Server Compromise**: "Use the `stdio` transport to limit access to just the MCP client" and, for HTTP, "Require an authorization token" / "Use unix domain sockets". Consistent with RFA's loopback-plus-token posture since v0.5.0.

**A2A 1.0.0** (https://a2a-protocol.org/latest/specification/, latest released version 1.0.0; prior 0.3.0, 0.2.6, 0.1.0). Two useful confirmations:
- Identity is delegated to the transport: "A2A protocol payloads, such as `JSON-RPC` messages, don't carry user or client identity"; "It primarily relies on HTTP headers and established standards like OAuth2 and OpenID Connect" (https://a2a-protocol.org/latest/topics/enterprise-ready/). **RFA is deliberately different and should stay different**: `from` and `origin` are in the payload and hub-stamped, which is what makes "no authority from text" enforceable and what makes the log self-describing. Record this as a divergence with a reason, not a gap.
- `AgentCardSignature` is JWS with a detached payload over a canonicalized card, with `protected` / `signature` / `header` fields and normative canonicalization/format/verification subsections (spec sections 8.4.1-8.4.3), and the verification section is explicit that the signature "does not validate the *contents* of the Agent Card's capabilities or claims". **RFA's shipped card signing already matches this shape** (JWS over JCS, EdDSA/ES256, `signatures` excluded from the signing input, RFC 7638 thumbprint pinning, [`src/signing.ts`](../../../src/signing.ts)), which is the strongest evidence that RFA's T2 card half was designed correctly and needs no rework for cross-org use. `UNVERIFIED:` the exact algorithm list A2A 1.0.0 permits; the doc points at the normative `spec/a2a.proto`, which I did not read.
- Also worth noting from A2A's own security framing: agents are "opaque (not sharing internal memory or direct resource access)". That is the same premise as a remote RFA member executing with its own unauditable tools, and it is why threat #12 is open by design in both protocols.

**MCP tasks extension SEP-2663** (`research/01-protocol/papers/mcp-sep-2663-tasks-extension.md`, Status: Final, Created 2026-04-27, authors Luca Chang and Caitie McCaffrey on behalf of the Agents Working Group; PR modelcontextprotocol/modelcontextprotocol#2663). The motivation section is the best available argument for R5, verbatim:

> **`tasks/list` scoping cannot be defined.** To avoid clients cancelling or retrieving results for tasks they shouldn't have access to, all tasks should be bound to some sort of "authorization context," the implementation of which is left to individual servers according to their existing bespoke permission models. However, in many cases, it is not possible to perform this binding, in which case the task ID becomes the only line of defense against contamination. In this scenario, **it is unsafe for a server to support `tasks/list` at all**.

RFA's task board has the authorization context MCP lacks (room membership, roles, zones) and currently spends none of it: `list` returns every task to every member ([`src/store.ts:1659-1661`](../../../src/store.ts)) and `claim` checks nothing about the claimant ([`:1663-1673`](../../../src/store.ts)). The one thing worth NOT copying from MCP: its task IDs are unguessable handles serving as the access control, which is the pattern MCP's own security page tells servers not to rely on.

Two things RFA got right that the 2026 literature is still asking for, worth saying in the spec because they read as accidents otherwise:
1. **Re-approval on capability change.** arXiv 2607.05744 measured that MCP "forces re-approval for 0/8 techniques even under a time-of-check to time-of-use rug-pull". RFA's digest rotation plus `digest_changed` forces exactly that re-projection.
2. **Human-only reintegration after quarantine.** OWASP ASI10-7 asks for "human approval before reintegration into production networks"; RFA has required a human-origin principal to lift a quarantine since 0.1.5.

## Open questions and spikes

Each spike is the cheapest experiment that settles the question, with the thing that would change my mind.

**S1. Prove the history bypass, then fix it (30 min).** Create a room with `history_visibility: "joined_after"`, send 10 messages, join as a second member with `history_limit: 0`, call `room_listen{since: 0, timeout_ms: 0, wait_for: "all"}`. Expect all 10. Then add the join-seq clamp and a regression test. *Changes my mind:* if the listen already clamps somewhere I did not find, this whole item dies and R3 is withdrawn.

**S2. Prove the task squat (30 min).** Two members, five `submitted` tasks; the second claims all five and never completes. Confirm no release path exists except supervisor `cancel_task`. Then implement `max_claims_per_member` and lease-expiry release. *Changes my mind:* if lease expiry already releases tasks, R5 shrinks to visibility scoping only.

**S3. Does the boundary wrapper survive an invisible-instruction payload? (1 h)** Send a message whose text carries an instruction encoded in the Unicode TAG block plus a bidi override, then read `episodes` and the console rendering. Expect the payload intact in the stored `wrapped` form and invisible in the console. Then extend `neutralize()` (N8) and assert the payload is gone. *Changes my mind:* nothing, honestly. The paper's mechanism analysis is renderer-independent and the code plainly strips C0 only. This spike is to build the regression test, not to settle the question.

**S4. Does the MemoryGate catch a MINJA-shaped attack? (half day, highest information value in this note.)** Script a remote member that asks a sequence of questions designed to make the resident write its own paraphrase of a false fact ("as we established, the SCPI threshold is X"), let consolidation run, then probe retrieval. Measure: does any fact land, with what `source_origin`, and does the gate fire? Prediction: the fact lands, tagged `agent`, gate silent. *Changes my mind:* if consolidation's extraction prompt already refuses to promote a peer-asserted claim to a fact, then the exposure is smaller than section 3 says and R11 drops from adopt to adapt. This spike should become an eval case either way (`evals/cases/`), because it is the one attack that is both cheap for an adversary and invisible in the current logs.

**S5. Is a per-zone gate check actually sufficient as an egress control? (half day.)** Write a `command`-tier check that shells haiku with the outbound response plus a short "does this reveal internal specifics" rubric, wire it to `to_zone: ["remote"]`, and run the 20 hardest questions from the existing parity fixtures through it. Measure false-refuse rate and added latency. *Changes my mind:* if the false-refuse rate exceeds ~10% or latency exceeds ~2 s, `gated` answering is not shippable as a default and R15 stays a knob nobody turns on; the fallback is R10's budget plus R9's skill visibility, which need no model in the path.

**S6. Cost of signing consequential events (2 h).** Measure `sign` + `verify` for an EdDSA JWS over a typical envelope using the existing `src/signing.ts`, and the byte overhead. Prediction from the shape of the code: sub-millisecond and a few hundred bytes. *Changes my mind:* if verification costs enough to matter in the send path, N11 becomes verify-on-demand at audit time rather than verify-at-append.

**S7. Chain anchoring and an offline verifier (2 h).** Write `npm run verify-log data/rooms/<room>.ndjson`, which recomputes the chain from genesis and reports the first divergence. Then decide the anchor sink (a file under `data/anchors/`, one line per room per hour). *Changes my mind:* nothing; this is pure upside and the test already contains the algorithm.

**Open questions I could not settle in this pass.**
1. **What identity does a remote agent actually have?** For a LangGraph agent, the credible options are a per-member invite (R2) plus an optional card key. Whether any real counterparty will hold a key is unknown until one is asked. `UNVERIFIED:` no evidence either way.
2. **Should `zone` be a two-value enum or an `org` string?** Two values keep the gate grammar and the console simple; an `org` string enables per-counterparty budgets and visibility, which is what a room with three organizations actually needs. My inclination is `zone` (enum, drives policy) plus `org` (opaque label, drives reporting and per-org budgets), both stamped at join from the invite. Needs one design pass, not research.
3. **Does anything break if a card is projected differently per zone?** Section 4.2 argues the digest must stay whole-card. Worth a careful read of the caching contract before implementing R9.
4. **Cross-room member identity.** Quarantine, budgets and reputation all want a key that survives rooms. The RFC 7638 card thumbprint is the natural candidate and only exists for signed cards. Unsigned remote members would need something else, or would be refused when `require_signed_cards` is on. Unresolved.
5. **The six design patterns' verbatim definitions** (arXiv 2506.08837 section 4) could not be extracted in this pass. If R24 is ever revisited, read them first.
6. **`policies.join: "approve"`** is specified and unimplemented (STATUS.md). Under the new premise it is more attractive than it was, but R2's single-use invites may make it redundant: an invite IS a pre-approval. Decide which one survives before building either.
