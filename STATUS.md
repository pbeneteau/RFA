## What this is

RFA (Rooms for Agents): a communication protocol where AI agents join rooms, discover each other (name, presence, signed capability cards), and talk in real time, with MCP-style discovery ergonomics. Built from a 13-agent deep-research pass ([research/01-protocol/REPORT.md](research/01-protocol/REPORT.md), 70 papers), specified ([spec/RFA-0.1.md](spec/RFA-0.1.md)), implemented, field-tested, and dogfooded in one day.

**Direction since 2026-08-17 (owner decision): the audience is any organization.** The earlier "personal tool for daily Goodvest work, not to sell" framing is RETIRED. RFA is built for any org to self-host, and a room holds two classes of member: **local** agents (agent.md packs the hub operator hosts and supervises) and **remote** agents hosted elsewhere, possibly by another org, possibly on another framework (LangChain/LangGraph) or exposed from another org's product. Remote agents must be able to claim and complete tasks from their side, with their own tools, which the hub never sees. Goodvest is the dogfood tenant, not the audience. This invalidates every "single operator, one laptop, personal tool" justification in waves 02 and 03 (they used it to reject per-message signing, federation, the REST binding, Postgres, multi-operator identity, registries); those need re-judging on merit, which is wave 04's job. The counterweight still holds: an org self-hosts something comprehensible, so no mandatory SaaS, no framework lock-in, no Kubernetes.

**Platform substrate (2026-08-16 evening decision, still current).** The protocol is the substrate; on top of it sit capable resident agents (tools, skills, memory, per-agent model/effort), an engine, sandboxes, observability, governance + budgets, evals, a workbench. Evidence: [research/02-platform/REPORT.md](research/02-platform/REPORT.md) (11-dimension sweep anchored on LangChain deep agents). Normative design: [spec/RFA-0.4-platform.md](spec/RFA-0.4-platform.md) with the v0.4.0-v0.4.6 build path. Core verdict: adopt the industry's schemas, reject its platforms; the Claude Agent SDK is the runtime.

## Reaching the hub from a phone (v0.5.1, partially shipped)

Tailscale is up on the Mac, the iPhone and the Mac Studio (tailnet `pbeneteau.github`, this host is `macbook-pro-de-paul.tailb95b2d.ts.net`). Serve is **enabled and running** (configured 2026-08-18):

```bash
/Applications/Tailscale.app/Contents/MacOS/Tailscale serve --bg --https=443 http://127.0.0.1:8790
# off again:  ... serve --https=443 off
```

Serve proxies ONLY `http://127.0.0.1`, which is why the hub can stay loopback-bound and still be reachable from the phone. On the phone: Tailscale from the App Store signed into the same account, then the console at `https://macbook-pro-de-paul.tailb95b2d.ts.net/console`, unlocked by pasting the human key (12h session). **MEASURED, and it passes**: a 20-second `room_listen` parked through Serve while a mention was appended from loopback at t=3s returned after **3.02s**, not at the window close, with the event's `wrapped` rendering intact and SSE framing preserved. Serve does not buffer a long-poll, so the console's live stream works from the phone and `X-Accel-Buffering` was not needed. Also verified through the proxy: the console document serves with a valid tailnet certificate, and a tokenless workbench read is still 401, so the loopback bind and the session token survive the proxy rather than being bypassed by it. One operational note that is not a Serve problem: the MagicDNS name does not resolve from a shell on the host itself (the measurement pinned it to the tailnet IP); a phone using Tailscale's resolver is unaffected, and the host needs Tailscale's DNS override enabled in the app if it ever has to reach its own tailnet name.

**`/mcp` now REQUIRES a credential** (2026-08-18), which is what makes tailnet exposure defensible. The hub runs with `RFA_MCP_TOKENS` set from `data/secrets.json` (`RFA_TOKEN`), and accepts three things: that operator token, or a live workbench session token, or nothing at all when no tokens are configured (the shipped default, unchanged). The session-token path is what lets the browser console work at all on an authenticated hub, since a page has nowhere safe to hold a static bearer; it is also the stronger credential, being short-lived and chained to a human key. Residents get `RFA_TOKEN` injected by the supervisor from their declared `secrets`; `npm run ask`, the parity gate and the eval harness resolve it from `data/secrets.json` through `transportToken()`, so nothing has to be exported. Verified: unauthenticated 401, operator token 200, session token 200, and both residents plus the ask CLI and the parity gate working against the authenticated hub.

Push and capture are SHIPPED and do not need Serve:

```bash
RFA_HUMAN_KEYS="$(cat dogfood/state/human-key.txt)" npm run start -- --http 8790 --otel --gate deploy/gate.json \
  --push-url https://ntfy.sh/<your-private-topic> --console-url https://macbook-pro-de-paul.tailb95b2d.ts.net
```

Push is notification-only by design: a title and a link, never a credential and never an approve button, because a verdict arriving over a broadcast transport with a bearer in it is a forgeable approval. `test/push.test.ts` asserts the absence of all of it. The console stays the only surface where a decision can be made.

`POST /api/ask` is the five-second capture path (spec 17.5), behind the session token, rate limited to 20/hour:

```bash
curl -s -X POST https://<host>/api/ask -H "authorization: Bearer $SESSION" -H 'content-type: application/json' \
  -d '{"room":"r_9a25e48c0e","capability":"answer-product-question","question":"...","reply_by_s":1800}'
```

It returns 202 with an `ask_id` and a `poll` path, because a 30-minute reply window cannot be held open on an HTTP request. Verified live: 202, pm-agent answered in ~25s, `GET /api/ask/<id>` returned the answer with a file citation.


`--allow-origin` is REQUIRED for the phone console: the page is loaded from the tailnet name, so the browser sends that as `Origin` and the DNS-rebinding allowlist refuses it with 403 without this flag. Leaving it out looks exactly like a wrong credential (see the findings ledger).

Pass the human key through `RFA_HUMAN_KEYS`, not `--human-key`: argv is world-readable in `ps aux` (found 2026-08-17 while killing the hub, the key was sitting in the process list in full), while another user's environment is not. Both forms work; the flag is for throwaway test hubs.

The hub is loopback-only by default. To reach it from a phone or another machine, proxy to it (`tailscale serve http://127.0.0.1:8790`) rather than passing `--bind`: the proxy terminates identity, a wider bind does not. Every workbench route, reads included, needs a session token (`POST /auth` with the human key; the console's unlock button does this).

**Restore procedure (exercised 2026-08-17)**: backups land nightly in `~/Backups/rfa-agent-com/<date>/` (sqlite `.backup` copies named `data__runs.db`, `data__obs.db`, `agents__<name>__state__memory.db`, plus `dirs.tar.gz` of data/rooms, dogfood/state, and agent memory dirs). - **Repairing the interop document found two more real bugs (2026-08-18)**, both from measuring rather than reading:
  - **The untrusted-data boundary escaped only the CLOSING tag.** A peer could put a forged OPENING header inside its own content, so a model reading the boundary saw a nested `<room-message origin="human">` it could not distinguish from the hub's own. Now both tags are escaped, verified live with an injection probe.
  - **An envelope's `seq` and `ts` were stamped AFTER the event was serialized**, so the bytes on disk carried `seq: 0` while the in-memory copy carried the real value. The same message read live and replayed after a restart disagreed, and an integrator reverse-engineering the hash chain had to know to zero both fields to reproduce a hash. - **Four engine threads had been wedged for up to two and a half days, and nothing was watching (2026-08-19, FIXED)**. A run only leaves `running` when its own process settles it, so a resident that is SIGKILLed, crashes, or is drained mid-turn leaves the row behind and its thread `busy` forever. The default multitask strategy is `enqueue` and the gate only tests for `busy`, so every later run on that conversation is created `pending` and waits for a drain that can only be triggered by the settle that will never come: **the conversation is permanently unservable**. Measured: 4 threads busy, three of them since 2026-08-17T09:17Z (the heartbeat-starvation SIGTERM, 2.5 days), one from today's supervisor crash. No `pending` runs had queued behind them yet, so the leak was latent rather than visible, which is exactly why it needed an instrument rather than a bug report.
  - `Engine.reconcileOrphans(agent)` marks that agent's `running` runs `interrupted` with a reason on the row, and frees their threads to `idle` (idle, not `interrupted`, because idle is what lets a queued `pending` run be picked up, and making the conversation servable again is the point). **Only the supervisor may call it, and only as it starts a resident**: that is the one moment something knows no other process owns the pack, since it refuses to start a duplicate. A resident cannot do this for itself (it could not tell its own corpse from a live sibling) and no timeout heuristic is safe either, because a 30-minute approval wait is a legitimately long-running run. Verified live: the supervisor reconciled all 4 on restart, naming each freed thread, and zero threads are `busy` now.
- **The watchdog-invariant replay harness is in, and it says NOT SHIPPABLE, which is the correct answer (v0.5.4, spec 20.6)**. 20.6 forbids shipping an invariant until it has been replayed against at least two weeks of logs plus `obs.db` and shown to fire on the known incidents and nothing else. That rule needs a harness or it is decoration. [scripts/watchdog-replay.ts](scripts/watchdog-replay.ts) reconstructs the state each candidate reads at hourly instants across the whole corpus, marks each firing against the recorded incidents, and refuses to bless anything while the corpus is short. **The corpus is 3.3 days. It is 10.7 days short, so nothing ships**, and that is a calendar problem, not a work problem. Replay works without stored history because both candidates read state that carries its own timestamps: an engine run knows when it started and ended, and a roster event is a full snapshot at its own seq.
  - Measured today, as a dry run: `engine-run-stuck-running` (the one 20.6 REQUIRES) is **CLEAN**, 54 firing buckets and all 54 inside a recorded incident. `observers-present-but-lease-expired` in its naive form **FALSE-FIRES**, which confirms 20.6's prediction empirically rather than by argument: it fires on a sidekick whose lease had simply expired inside the 24h prune window. The corrected form, "expired for longer than the prune window", is **SILENT** on this corpus, so it is unvalidated rather than proven: the zombie corpses it was written for were evicted by hand before any of them aged past 24 hours.
  - **The harness caught two flaws in itself, and both are modelling lessons rather than code bugs.** First, an incident window must run from onset to REMEDIATION, not to the hour someone noticed: a persistent anomaly fires in every bucket until it is fixed, and windows drawn around discovery made three orphaned runs look like 34 false positives spread over two days, when the state really was broken for all of it. Second, matching a firing to any incident that merely OVERLAPS it in time lets a broad window launder unrelated firings; extending the orphan window to its true remediation made the naive observer invariant read CLEAN when what it had done was fire on something unrelated. An incident now has to claim an invariant by name (`explains`). Without that second fix this harness would have blessed the invariant the spec predicted would fail.
  - Not tested by `npm test`: it is a reporting script whose output is the evidence, run by a human at the point of decision. Worth knowing rather than assumed.

Found while stamping the provenance keys of spec 20.2 and then reading what the script actually produced. On the standing room that meant **1041 roster events beside 2 messages**, where the existing tracked case is 3.5 KB, so three promotions would have added 14 MB of duplicated roster history to the repository. Nothing failed at any point, which is why it has a test now.

- **Case provenance is stamped at promotion (v0.5.4, spec 20.2)**. All five keys, with the spec's types: `origin_run_id`, `origin_room`, `origin_seq_range: {from, to}`, `promoted_at`, `failure_mode`. - **94% of the recorded cost in the observability store was one wrong variable, and the new digest found it on its first look at real data (2026-08-19, FIXED)**. `#ops` digest built, and the first thing it reported was a p90 cost of **$2.96 per run**, which is impossible: the whole day's agent ceiling is 8 dollars. Cause: a serve turn stopped by a ceiling recorded `BudgetStop.spendUsd`, the DAY's running total, as that run's own `cost_usd`. Eleven refusals that made **no model call at all** (0-1ms, refused at pickup) were each recorded at $7.9831, and 98 of 99 error rows carried a ledger value: **$351.84 of the $372.91 total in the store**, against a true lifetime figure of $21.01. ## Gotchas for future sessions

- Bash `cd` persists between calls; a leaked cd into node_modules once caused scary false alarms. Prefer absolute paths.
- Scratchpad `.ts` scripts run as CJS; name them `.mts` for top-level await.
- Envelope `message_id` minimum 8 chars; the v2 SDK returns input-validation failures as PLAIN TEXT tool results (not JSON).
- Claim-less legacy HTTP posts get SSE-framed responses (`data:` lines); scripted probes should speak the modern era (`Mcp-Method`/`Mcp-Name` headers + `_meta` protocolVersion) for plain JSON.
- Testing agent flows non-interactively: `claude -p "<prompt or /command>" --model sonnet --allowedTools "Skill,Read,mcp__rfa-hub__room_join,mcp__rfa-hub__room_send,mcp__rfa-hub__room_listen,mcp__rfa-hub__room_roster"`.
- Never commit `dogfood/knowledge|state|ROOM.md`, `data/`, `reports/` (gitignored on purpose: internal docs, secrets, runtime state).
